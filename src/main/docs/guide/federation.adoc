This page is a recipe for a federated subgraph: an application that answers the `_service` and `_entities` fields that a federation gateway sends. The library has no federation support. The recipe uses a `GraphQLSchemaCustomizer` (the supported API that it relies on) to add the two fields after the binding, and the code of the transform is application code that the example suites own and test. The tests check the subgraph contract (`_service` and `_entities`); they do not compose the subgraph with a gateway.

The transform of this page is written with graphql-java alone, so the recipe adds no dependency. An application can instead apply the transform of a federation library to the schema in the same customizer.

== The schema

The federation directives are declared in the schema like any other directive, and the entity types carry `@key`. `Product` is reachable from the root field `Query.product`. `Order` is an entity that no field returns, so only `_entities` reaches it:

The recipe declares `@key` with `fields: String!`. This declaration is the one the tests cover. The recipe does not import the directives of the federation specification through a federation `@link` declaration, so it does not test the other directives (such as `@shareable`, `@external` or `@requires`) or their federation semantics. A schema that declares a directive in the same way has to list it in the setting below as well.

== The transform

The customizer receives the schema that the library built, after the binding and the strict checks. The transform adds:

* `_Any`, a scalar that accepts the representations as a JSON value;
* `_Entity`, a union of the object types that carry `@key`;
* `_Service` with the field `sdl`;
* the fields `Query._service` and `Query._entities(representations: [_Any!]!)`, each with a data fetcher that asks a predicate about the caller first, and a type resolver for `_Entity`.

snippet::example.federation.FederationTransform[project-base="test-suite", source="test", tags="transform", indent="0"]

The `sdl` is the schema printed by graphql-java before the transform, so it includes the applied `@key` directives and the types of the whole application, and not the three added fields. The printer writes a `schema { ... }` definition when the root types have names other than `Query`, `Mutation` and `Subscription`. An application that serves a part of its schema prints or reads that part itself.

`FederationTransform.Entity` pairs the resolver function of an entity type with a predicate on the `GraphQLContext` that decides whether the caller may read it, and `apply` takes a predicate for `_service` as well. The constructor needs both, so the code that wires an entity type states who may read it. See <<federationAccess,Who may read>>.

== Entity resolution

A resolver function for each entity type turns a representation (the `__typename` and the key fields) into the entity. A function of this recipe returns an object of a `@GraphQLType` class (`ProductEntity`, which carries `@GraphQLType(name = "Product")`; a class without a name is matched by its simple name) or a `Map` that carries `__typename` (`Order`). The map is for an entity that no root field reaches: the binding does not bind a type that nothing reaches, so its fields are read by graphql-java's default data fetcher, which reads a `Map` without reflection. The customizer bean wires the functions and their predicates to the transform. It carries `@Order(Ordered.LOWEST_PRECEDENCE)`, so that it runs after the other `GraphQLSchemaCustomizer` beans of the application and the SDL and the `_Entity` members include what they add (see <<customizerOrder,The order of customizers and decorators>>):

== Who may read

The data fetchers of `_entities` and `_service` are added by the customizer, after the library applied its field decorators. `@Secured` on a resolver method guards the field that the method serves, and the entities fetcher is not that field. The fixtures of the suites secure `Query.product` for `ROLE_ADMIN`, and `Product` is an entity type as well. The test starts the subgraph twice: with the predicates of the recipe replaced by one that accepts a caller without a check, an anonymous caller is refused on `product` with the code `UNAUTHENTICATED` and receives the same product through `_entities`; with the predicates of the recipe in place, the same anonymous request to `_entities` is refused:

The predicates of the recipe read the `Authentication` that the security module puts in the `GraphQLContext` (see <<security,Security>>). A caller without an entry, which is an anonymous caller, is refused:

The customizer above gives `Product` to `ROLE_ADMIN`, `Order` to `ROLE_BILLING` and `_service` to `ROLE_ADMIN`. The predicate compares the roles of the `Authentication` with the role; it does not call the `RolesFinder` bean. The security module and Micronaut Security are test dependencies of the suites; the transform itself does not use them.

A refused request gets HTTP status 200 and a response without `data`, with an error whose `extensions.code` is `FORBIDDEN`. The fetcher asks the predicate of the type of each representation. === Restrict the route

A URL rule of Micronaut Security on the GraphQL path decides who reaches the endpoint. The test sets the rule below. An anonymous request to `_service` or to `_entities` gets status 401, and the response does not contain the SDL or the entity. An authenticated request passes the route and then meets the predicates, so a caller with `ROLE_USER` is refused as above, and a caller with `ROLE_ADMIN` receives the product:

----
micronaut.security.enabled=true
micronaut.security.intercept-url-map[0].pattern=/graphql
micronaut.security.intercept-url-map[0].access[0]=isAuthenticated()
----

snippet::example.federation.FederationSecurityTest[project-base="test-suite", source="test", tags="route", indent="0"]

The other tests of `FederationSecurityTest` set the rule `isAnonymous()` on the same path, so that the predicates decide.

The test suites run the example with strict mode at its default, and two checks find the federation schema. The directive `@key` has no wiring, and `Order` is reachable through `_entities` only, which is added after the checks run. Two settings accept them:

== What is recipe and what is supported API

* Supported API that the recipe uses: `GraphQLSchemaCustomizer`, `GraphQLTypeDefinitionRegistryCustomizer`, `@GraphQLType`, `@GraphQLRootResolver`, the `allow.inert-directives` and `allow.unreachable` settings, and for the predicates the `GraphQLSecurity.AUTHENTICATION_KEY` entry of the context.
* Recipe, owned by the application: the `_Any`, `_Entity` and `_Service` types, the two fields, the entity resolver functions, their predicates and the SDL that `_service` returns. The library does not test them against a federation gateway, and a change to the specification is not followed by the library.

== Limits

* The fetcher of `_entities` returns an error for a request with more than 100 representations, for a representation that is not an object, for one without a string `__typename`, and for a type that has no resolver function. The limit of 100 is a constant of the recipe; `FederationTest` has a test for each of these cases.
* The type resolver of `_Entity` reads the name of a class from `@GraphQLType(name = ...)` or uses its simple name. A class that a `GraphQLSchemaMappingDictionaryCustomizer` maps to another name is not looked up there.
* The tests call the endpoint at `/graphql` over HTTP. They do not call `_entities` or `_service` over WebSocket.
* The tests run with the default `RolesFinder`.
* The entity resolver functions are plain graphql-java data fetchers. They do not use data loaders or the resolver parameters of the library.
* An entity that no root field reaches is not bound by the library. The recipe returns a `Map` for it. A class there would be read by graphql-java through reflection, which a native image needs metadata for.
* The Java and Kotlin suites run `FederationTest` and `FederationSecurityTest` as native tests (`:test-suite-java:nativeTest` and `:test-suite-kotlin:nativeTest`). The Groovy example is a Spock specification, which does not run natively, so the page claims no native test for it. See <<nativeImage,Native Image>>.
