The `micronaut-graphql-tools-security` module integrates Micronaut Security: the `Authentication` of the request reaches the resolvers, `@Secured` guards resolver methods, and a hook sees the root fields of an operation after the document is parsed. The core library does not depend on Micronaut Security: its beans exist only when the application has it. It is available since 1.0.0-M4.

== The module

[source,groovy]
----
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-security")
implementation("io.micronaut.security:micronaut-security")
----

The version comes from the `micronaut-graphql-tools-bom` import of the quick start.

`micronaut.graphql.tools.security.enabled` (default `true`) turns the beans of the module off: the contributor, the decorator of `@Secured` and the `Instrumentation` of the root fields hook. With it `false`, `@Secured` guards nothing, no api:io.micronaut.graphql.tools.security.GraphQLRootFieldsHook[] bean is called, and a hook bean that nothing else injects is not even created. Micronaut Security authenticates the request as it always does, with its filter, its fetchers and its rules, and this module adds nothing to that. A URL rule on the GraphQL path decides who may reach the endpoint at all, for example `isAnonymous()` when the schema guards its own fields.

== The principal in a resolver

A resolver declares `Principal`, or `Authentication`, as a parameter, see <<resolverParameters,Resolver Parameters>>. The value is the one that Micronaut Security set on the request, and it is `null` for an anonymous request. It is read from the request that the execution captured, never from a thread-local, so a field that runs after an async parent sees the same principal as the parent. The same holds over WebSocket, where the principal is the one of the upgrade request: the connection is authenticated once, and every operation on it runs as that principal.

The module also puts the `Authentication` in the `GraphQLContext` under `GraphQLSecurity.AUTHENTICATION_KEY`, once for each execution, with a api:io.micronaut.graphql.tools.execution.GraphQLContextContributor[]. The entry is absent for an anonymous request. `SecurityService` works in a field that runs after an async hop too, because the library restores the request in the continuation.

== Secured resolver methods

`@Secured` on a resolver method, or on the resolver class, guards the fields that it serves. The values are those of Micronaut Security:

[cols="2,5", options="header"]
|===
|Value |A call is allowed when
|`SecurityRule.IS_ANONYMOUS` |always. The field is left alone.
|`SecurityRule.IS_AUTHENTICATED` |the request is authenticated.
|A role, such as `ROLE_ADMIN` |the authenticated request has at least one of the listed roles.
|`SecurityRule.DENY_ALL` |never.
|===

A rejected call does not run the resolver. The field is `null` and the response has an error of that field, whose `extensions.code` is `GraphQLSecurity.UNAUTHENTICATED_CODE` (`UNAUTHENTICATED`) for an anonymous request, and `GraphQLSecurity.FORBIDDEN_CODE` (`FORBIDDEN`) for an authenticated one that lacks the role or that no request may call. A secured field of a non-null type makes its parent `null`, as every field error does, so a field that anonymous clients may call next to guarded ones should be nullable in the schema where that matters.

The decision is made once for each field, at startup, through the api:io.micronaut.graphql.tools.execution.GraphQLFieldFetcherDecorator[] of the library. A field without `@Secured`, and a field that allows anonymous callers, keeps the fetcher it had: nothing is added to its call, and the shortcuts that graphql-java has for trivial fetchers still apply. A secured field costs one context lookup and one set lookup. A call that passes allocates only the read-only view of the roles that `Authentication.getRoles()` of Micronaut Security returns: 72 bytes in the allocation benchmark, on the JDKs and graphql-java legs the build covers. An unsecured field allocates nothing more with the module installed than without it, and an allocation gate in the benchmarks fails the build if that changes.

=== Expressions are rejected

Micronaut Security also reads `@Secured` values that are expressions, such as `@Secured("#{user.name == 'x'}")`, and evaluates them against the HTTP route of a request. A GraphQL field is served by one route for all fields, so the expression has no field to be about, and the module does not evaluate expressions. It does not treat them as role names either, because a check that never matches would hide the mistake. An application that starts with such a value on a resolver method fails at startup with a `ConfigurationException` whose message names the resolver method (the declaring class and the signature) and the coordinates of the field (for example `Query.secGated`) and says that the value is an expression value. Use the values of the table above, or decide in the resolver with `SecurityService`. The check runs only while the module is enabled.

=== Roles and `RolesFinder`

A role check goes through the `RolesFinder` bean of the context, as it does for routes: `hasAnyRequiredRoles(requiredRoles, grantedRoles)` decides whether the roles of the `Authentication` satisfy the roles of `@Secured`. An application that replaces the bean, for example to map the roles of its identity provider to the roles of its application, changes the decision for secured fields too:

It is the same bean that decides on the URL rules of Micronaut Security, whose granted roles also carry the markers such as `isAuthenticated()`, so a replacement keeps those markers and delegates the rest to the default method, as the example does. With the default `RolesFinder` the decision is a set lookup made without calling the bean, so the default costs nothing more than before. A replaced bean is called once for each secured field of an operation that reaches the check.

== The root fields hook

An application that decides on the fields of an operation, for example to rate limit a mutation, would parse the request body a second time in an HTTP filter. A `GraphQLRootFieldsHook` bean sees the operation once the library's execution has parsed and validated it, before any field is fetched:

snippet::example.tck.SecurityScenario[project-base="test-suite", source="test", tags="root-fields-hook", indent="0"]

The names are field names, not aliases, in document order and without duplicates, and the fields of fragments are included. `@skip` and `@include` are not applied. The hook receives the `GraphQLContext`, with the authentication in it. It throws `AbortExecutionException` to reject the operation: its message is the error of the response and no field is fetched. The hooks run in the order of `@Order`. The module installs its `Instrumentation` only when the application has a hook bean, so an application without one pays nothing.

== Cost

The contributor runs once for each execution and reads one request attribute. With at least one `GraphQLContextContributor` bean, the library creates a data loader registry for each execution, see <<context,Context>>.
