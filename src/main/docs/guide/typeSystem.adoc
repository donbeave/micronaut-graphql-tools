This page covers the Java types behind the GraphQL types: the return types of resolvers, enums, the classes of union members and interface implementations, the mapping dictionary, and Java interfaces as object types.

== Return types

A resolver method returns the Java type that matches the GraphQL type of its field, optionally in the wrappers below. They are peeled in this order, each at most once, and the startup (and, with the processor, the build) fails with `[unsupported-return-type]` for any other shape:

. `CompletionStage<T>`, at the field itself and never inside a list;
. `Publisher<T>`: the stream of a field of the subscription type, and the reactive value of every other field (below);
. `DataFetcherResult<T>`, to return data with errors or a local context;
. `Optional<T>`, `OptionalInt`, `OptionalLong` and `OptionalDouble`, for a nullable GraphQL type only (an empty one becomes `null`).

=== Reactive return types

A method of a Query, Mutation or type field can return a `Publisher` instead of calling `toFuture()` itself. The library subscribes to it once for each call and hands graphql-java a `CompletionStage`. The decision is made once for each field at startup, from the declared return type, so a field that does not return a `Publisher` costs nothing extra. The library has no dependency on a reactive library: `Publisher` is the Reactive Streams interface, and the code below uses Project Reactor, which your application brings (for example with `micronaut-reactor`).

snippet::example.tck.ReturnTypesScenario[project-base="test-suite", source="test", tags="publisher-returns", indent="0"]

* A single-value publisher gives the value of the field, and an empty one is `null`. The single-value types are named once, by their class name: `Mono`, the `Single`, `Maybe` and `Completable` of RxJava 3 (`io.reactivex.rxjava3.core`) and of RxJava 2 (`io.reactivex`), and Micronaut's `CompletableFuturePublisher`. Any other `Publisher` is a single-value publisher on a method that is annotated with `@SingleResult`. A `Completable` emits no value, so its field is `null`: declare the field without `!`. A `Completable` on a field with `!` fails startup, and the compile-time check, with `[unsupported-return-type]`; the message names the field and the fix. The RxJava types are converted through Micronaut's reactive converters: add `micronaut-rxjava3` or `micronaut-rxjava2` to the application.
* A publisher of many values (`Flux`, an RxJava `Flowable` or a plain `Publisher`) needs a list field. The values are collected into the list, in order. An empty `Flux` is an empty list.
* An error signal is an error of that field, like an exception thrown by the method or a failed `CompletionStage`: the field is `null` (or the nearest nullable parent, for a non-null field) and the rest of the response is unchanged.
* A `Mono` can be wrapped in `DataFetcherResult` or `Optional` inside, as `Mono<Optional<T>>`. For a `Flux`, the wrappers apply to each element: `Flux<DataFetcherResult<T>>`.
* A `Flux` on a field that is not a list fails the startup, as does a `Publisher` inside a `CompletionStage`, inside a list, or on a bean property (a property is read, not invoked). An `Observable` of RxJava is not a `Publisher`; convert it with `toFlowable()` first.
* A field of the subscription type is different: its `Publisher` is the stream of events and is not collected.

The adapted future completes on the thread that signals the publisher. The adaptation itself neither captures nor restores a propagated context: that belongs to the execution model of the library, and a reactive library that propagates the context on its own (as `micronaut-reactor` does) keeps doing so.

[[typeDictionary]]
== The classes of union members and interface implementations

A field that returns an object type tells the library its class through the return type. The members of a union and the object types that implement an interface are not named by any return type, so each needs a class. Four sources give it, and the first one that has an answer wins:

. *The dictionary.* `SchemaMappingDictionary.registerType("Book", BookModel.class)`, from a api:io.micronaut.graphql.tools.customizer.GraphQLSchemaMappingDictionaryCustomizer[] bean, always wins. It is the escape hatch for a class that no rule below finds.
. *`@GraphQLType(name = "Book")`* on the class. The class stands for the object type of that name. The annotation is read from the bean introspection, so the build-time processor and the startup see the same declaration.
. *The naming convention* `micronaut.graphql.tools.type-class-convention`, a pattern that holds `{Type}` once. With `{Type}Graph`, the object type `Book` is the introspected class whose simple name is `BookGraph`. A class that declares a name with `@GraphQLType(name)` is matched by that name only. There is no convention by default.
. *The permitted subclasses of a sealed type.* When the Java type that the field declares for the union or the interface is sealed, the object type is the permitted subclass whose `@GraphQLType(name)`, or, where it declares none, whose simple name, is the type name. The member list stays in the schema; the sealed type only says which class is each member, so the same schema gives the same members in Java, Kotlin and Groovy. See <<sealedTypes,Sealed types>>.

snippet::example.tck.TypeClassDerivationScenario[project-base="test-suite", source="test", tags="type-classes", indent="0"]

With `type-class-convention: "{Type}Graph"`, `DerivedBook` and `DerivedPoster` match `DerivedBookGraph` and `DerivedPosterGraph`, `DerivedMagazine` is declared by its annotation, and the dictionary maps `DerivedPoster` to `PosterPrint`, which wins over `DerivedPosterGraph`. The union needs no other entry.

Two classes that match one object type, by the annotation, by the convention or one by each, fail the startup with `[ambiguous-type-class]` naming the type and both classes. A dictionary entry for that type ends the ambiguity, because an explicit entry always wins. A convention without `{Type}`, or with it twice, fails the startup with `[invalid-type-class-convention]`.

The same three sources name the class of an interface that no field returns, so that a @api:io.micronaut.graphql.tools.annotation.GraphQLTypeResolver[] of that interface binds its fields on every implementation. Register the interface in the dictionary (`registerType("Node", Node.class)`), annotate it with `@GraphQLType(name)`, or let the convention find it. An implementation that binds the same field itself, with a member or a resolver of its own, is still reported: `[multiple-methods-found]` for two resolvers, and the `precedence` rules for a member. The dictionary entry of such an interface counts as used, so `strict` reports no `[unused-dictionary-entry]` for it.

The derivation reads the compile-time introspection metadata only, so it works in a native image and adds no reflection. It runs once for each type at startup. A request resolves the object type of a value through a cache with one entry for each runtime class, and does no lookup of a name.

[[sealedTypes]]
=== Sealed types

A union or an interface whose Java type is sealed needs no dictionary entry and no naming convention:

snippet::example.tck.SealedTypesScenario[project-base="test-suite", source="test", tags="sealed-types", indent="0"]

`SealedCircle` and `SealedSquare` are found because they are permitted subclasses of `SealedShape` and carry the names of the object types; `SealedDog` and `SealedCat` implement the interface `SealedPet` in the same way; the dictionary maps `SealedTriangle` to `ThreeSidedShape`, which has another name, and an explicit entry is used as before.

The rules:

* Java sealed types (a `permits` clause, or subclasses in the same compilation unit), Kotlin `sealed` classes and interfaces, and Groovy `sealed` classes and interfaces with a `permits` clause are all sealed types, and the rule is the same for each. Groovy needs the sealed type on a JVM that supports it (Java 17 or later).
* Only the permitted subclasses that are introspected (@api:io.micronaut.graphql.tools.annotation.GraphQLType[], `@Introspected`) are members, because the binding reads their properties through the introspection. An abstract or sealed intermediate class is not a member; its own permitted subclasses are.
* Where no permitted subclass has the name of a member, the member has no class, as it has none without a sealed type: the startup fails with `[union-type-mapping-not-provided]` or `[interface-type-mapping-not-provided]`.
* A type that is not sealed is not affected: its members are found by the dictionary, `@GraphQLType(name)` or the naming convention only.
* The derivation reads no permits clause by reflection: every subclass of a sealed type is one of its permitted subclasses, so the introspected classes that the sealed type is assignable from are the candidates. It works in a native image and runs once for each type at startup.
* The compile-time checks do not derive the members from a sealed type: the startup decides, and a sealed type adds no compile-time finding.

=== Compile-time check

The processor reports `[ambiguous-type-class]` at compile time with the same rule and the same message as the startup. It sees the classes of the module that carry `@GraphQLType` or `@Introspected` (a class that only @api:io.micronaut.graphql.tools.annotation.GraphQLModels[] or a dependency introspects is not seen), the schema files of `schema.dirs`, and the processor option `micronaut.graphql.tools.processor.type.class.convention`, which holds the value of the runtime key. The dictionary is runtime code, which a visitor cannot see, so a build reports two matching classes even when a dictionary entry ends the ambiguity at startup. Remove the annotation or rename one class, or compile with `micronaut.graphql.tools.processor.checks=false` and let the startup decide. A class of another module is a candidate at startup only.

== Enums

A GraphQL enum maps to a Java enum. The enum needs a bean introspection (`@Introspected`; a `@Serdeable` enum has one too), and the library reads its constants from that introspection at startup and registers one values provider for each bound enum. graphql-java then coerces an enum argument, an enum input field or a schema default value to the Java constant, and serializes a returned constant by its schema name. The resolver receives the constant, with no conversion call:

snippet::example.tck.EnumsScenario[project-base="test-suite", source="test", tags="enums", indent="0"]

* The schema name of a value is the name of the Java constant.
* A Java enum without an introspection fails the startup with `[class-not-introspected]`, and the message names `io.micronaut.core.annotation.Introspected`.
* A schema value without a constant fails the startup with `[missing-enum-values]`.
* A constant without a schema value is the check `unbound-enum-constant`; `@GraphQLIgnore` on the constant says that it is left out on purpose (see <<strictMode,Strict Mode>>).
* A value that the schema does not define is a request error from graphql-java, and the resolver is not called.
* A `GraphQLRuntimeWiringCustomizer` that registers its own `enumValues` for a bound enum replaces the library's wiring and fails the startup with `[runtime-wiring-override]`.

[[mappingDictionary]]
== The schema mapping dictionary

A `GraphQLSchemaMappingDictionaryCustomizer` bean registers the Java class of an object type that no return type names, such as a member of a union. Several customizers can exist, for example one for each module: they run in `@Order` on one dictionary, and a GraphQL type that two of them map fails the startup.

snippet::example.tck.AbstractTypesScenario[project-base="test-suite", source="test", tags="mappings", indent="0"]

A GraphQL type can be mapped to a class or to a Java interface. An interface and the classes annotated with `@GraphQLType(TheInterface.class)` are one mapping when each such class implements the interface (the startup fails with `[incorrect-implementation]` for one that does not): an object of any of those classes resolves to that object type, and a field may declare either the interface or such a class for the same GraphQL type. The startup checks these rules:

* A GraphQL type is mapped once, and a Java type is mapped to one GraphQL type. The error names the GraphQL types and the Java types involved.
* Mapping one GraphQL object type to an interface and another one to a class that implements it fails with `[ambiguous-type-mapping]`, because an object of that class would match both.
* Two fields that declare different Java types for one GraphQL type fail with `[mapping-conflict]`, unless the two types are an interface and a class annotated with `@GraphQLType(TheInterface.class)` that is read through the same bean introspection.
* A class and its subclass can be mapped to two GraphQL types. A union or an interface resolves an object of either class by its exact class.

The entries that the other sources of the <<typeDictionary,classes of union members>> section find need no dictionary entry. An entry that nothing uses is the check `unused-dictionary-entry` (see <<strictMode,Strict Mode>>).

== Unions and interfaces

A field that returns a union or an interface declares a Java interface, such as `List<Media>` for `[Media!]!`; a class fails the startup. The classes in the example above are the members:

* Each member of a union, and each object type that implements an interface, needs a class (see <<typeDictionary,the sources of that class>>). Without one the startup fails with `[union-type-mapping-not-provided]` or `[interface-type-mapping-not-provided]`.
* Each of these object types is bound like any other, so each field of an interface is bound on each implementation. That an object type declares all the fields of its interfaces is checked by graphql-java.
* The class of a member has to be one that an object of the field could be an instance of. The startup fails with `[incorrect-member-mapping]` for a mapping that cannot match: a `final` class that does not implement the declared Java interface, or two classes with no subtype relation.
* An interface that no field returns but that a bound object type implements is bound too, and is not an unreachable type.

At runtime the object type of a returned object is chosen in two steps, and the result is cached for each class:

. The *exact class*: the class that an object type is mapped to, or, for an object type mapped to a Java interface, a class annotated with `@GraphQLType(TheInterface.class)`.
. *Assignability*: otherwise the object type whose Java type the object is an instance of, which covers a subclass of a mapped class (a runtime proxy, for example) and an implementation of a mapped Java interface. When the object is an instance of several, the object type whose Java type is a subtype of all the others wins.

An object that matches no object type is an error on that field, and the data of the field is `null`. So is an object whose candidates have no single most specific one, such as a class that implements two mapped interfaces. The error names the union or interface, the path, the class and the candidates. At startup, a class with an introspection that is an instance of the Java types of several members of a returned union or interface, with none more specific, fails with `[ambiguous-abstract-type]`, which names the class and the members. A class without an introspection can only be checked at runtime.

A type resolver of the Java interface that an SDL interface is mapped to binds the fields of that interface on each implementation that does not bind them itself (see <<binding,Binding>>).

== Java interfaces as object types

A field may declare a Java interface for an object type. Where the properties come from depends on whether the interface has a bean introspection of its own:

* *The interface is annotated with `@GraphQLType` or `@Introspected`.* The properties are the getters that the interface declares, read from an object of any class that implements it. The implementing classes need no annotation. A `@GraphQLTypeResolver(TheInterface.class)` method receives the object as the interface.
* *The interface has no introspection of its own.* The library reads one class annotated with `@GraphQLType(TheInterface.class)`, with all of its getters, including getters that the interface does not declare. No such class fails the startup with `[implementation-not-found]`, and several fail it with `[multiple-implementations-found]`. The check `interface-read-through-implementation` reports this case at its default severity, so annotate the interface, or set the check to `warn` or `ignore` (see <<strictMode,Strict Mode>>).

A getter that only an implementation class declares is not a property of an interface that has its own introspection. A field that only such a getter could serve fails with `[field-not-bound]`; declare the getter on the interface, or serve the field with a `@GraphQLTypeResolver` method of the interface. At startup the library logs one INFO line for each object type mapped to a Java interface, which names the interface and the way its properties are read.
