Two optional modules record what the library executes, each named after its technology: `micronaut-graphql-tools-micrometer` records request metrics with Micrometer, and `micronaut-graphql-tools-opentelemetry` records request and field spans with OpenTelemetry. They follow the way the Micronaut Micrometer and Micronaut Tracing modules work. This page describes what they record, the conventions they follow, how to select the fields that get a span, how to time and trace your own resolvers, and what they cost. Both modules are available from 1.0.0-M4.

== The modules

Add the module of the technology you use, or both, and the Micronaut integration it needs:

[source,groovy]
----
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-micrometer:1.0.0-M4")
implementation("io.micronaut.micrometer:micronaut-micrometer-core")

implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-opentelemetry:1.0.0-M4")
implementation("io.micronaut.tracing:micronaut-tracing-opentelemetry")
----

The modules do not depend on each other, and neither has Micrometer or OpenTelemetry as a dependency. The metrics need a `MeterRegistry` bean, which Micronaut Micrometer provides. The tracing needs an `OpenTelemetry` bean, which Micronaut Tracing provides from the `otel.*` properties and exports to the `SpanProcessor` beans of the application. With neither bean the library installs no instrumentation. The tests use a meter registry, and a span processor that exports to memory:

Both follow the conventions of the Micronaut module that provides their library:

* Metrics are a Micronaut metrics binder named `graphql`. They obey `micronaut.metrics.enabled` and `micronaut.metrics.binders.graphql.enabled`, as the binders of Micronaut Micrometer do.
* Traces use the OpenTelemetry `Instrumenter` API, as the HTTP, Kafka and gRPC integrations of Micronaut Tracing do. They obey `micronaut.otel.enabled`, and the keys under `micronaut.graphql.tools.tracing`.

== Instrumentation beans

The library collects every `Instrumentation` bean and installs them before the `GraphQLBuilderCustomizer` beans run. One bean is installed as it is. Several are chained in a `ChainedInstrumentation`, lowest order first (`@Order` or `Ordered`), so the `beginExecution` of the lowest order runs first. With no `Instrumentation` bean the library sets no instrumentation, and graphql-java keeps its default. A customizer that calls `instrumentation(...)` on the builder replaces what the beans installed.

The library adds exactly one `Instrumentation` bean for observers, whichever modules are on the classpath. It lives in `graphql-tools` and exists only when an observer bean does: each module contributes one observer (the Micrometer module a `RequestObserver` that records the timer, the OpenTelemetry module one that starts the request span) when its technology is on the classpath and its bean (`MeterRegistry` or `OpenTelemetry`) exists. Two instrumentations in the chain would cost every field about 550 bytes on graphql-java 21, which is why the modules share one. It implements the request hooks only and nothing at field level, so an execution that it observes pays nothing for each field. The library itself uses no `Instrumentation`: an operation's fields run through the data fetchers that the binding created, and the spans of the OpenTelemetry module wrap only the fields that you select. `RequestObserver` is `@Internal`: it is not an extension point for applications, whose own `Instrumentation` beans are chained as above.

== Metrics

The module is `graphql-tools-micrometer`.


The request timer is `graphql.request`, from the start of the execution to its result. Its tags:

[cols="2,5", options="header"]
|===
| Tag | Value
| `operation` | The operation name, from the operation of the document or from the request. A request without a name is `anonymous`. A client chooses the name, so the module keeps at most `micronaut.metrics.binders.graphql.max-operations` distinct names (default 100); every name beyond the cap is `other`. The cap is exact under concurrent requests.
| `outcome` | `success`, or `error` when the execution failed or its result has an error.
|===

A field has no timer of its own: see <<resolverTimers>> for how to time one. The meter names and tags are constants in `GraphQLMetrics`.

A subscription is timed until its stream is set up, not until it completes.

=== DataLoader metrics

`graphql.dataloader.batches` counts the batches that the `DataLoader` of a batch loader bean dispatched, and `graphql.dataloader.batch.keys` the keys those batches loaded. Each is tagged with `loader`, the name of the batch loader bean. They are recorded when the request ends, from the counts that the library keeps for the execution (`DataLoaderBatchStatistics` in the GraphQL context). Counting adds two atomic increments to each batch, so the library counts nothing by default: set `micronaut.graphql.tools.execution.data-loader-statistics` to `true` to get these meters. Without it no DataLoader meter exists.

=== Timers for your own resolvers

The library records no timer for a field. A timer for a resolver is `@Timed` (`io.micrometer.core.annotation.Timed`), which Micronaut Micrometer handles for any bean method. It needs the processor `micronaut-micrometer-annotation` in the annotation processor path (in the `ksp` configuration for Kotlin, and on the compile classpath for Groovy), and a `MeterRegistry` bean.

== Tracing

The module is `graphql-tools-opentelemetry`.


Each request is one span, started with an OpenTelemetry `Instrumenter` in the instrumentation scope `io.micronaut.graphql.tools`, with the kind `INTERNAL`. It is a child of the span that is current when the execution begins: the span of the HTTP request when the application has the HTTP server integration of Micronaut Tracing (`micronaut-tracing-opentelemetry-http`).

The span and its attributes follow the OpenTelemetry semantic conventions for GraphQL:

[cols="2,5", options="header"]
|===
| Name | Value
| Span name | The operation type: `query`, `mutation` or `subscription`. The name of the operation is part of the span name only when `micronaut.graphql.tools.tracing.add-operation-name-to-span-name` is `true`, which gives `query GetUser`: a client chooses the operation name, so the default keeps it out of the span name, whose values should be few. A request that never reaches an operation (it does not parse or validate) is named `GraphQL Operation`.
| `graphql.operation.type` | `query`, `mutation` or `subscription`. Absent when the request never reaches an operation.
| `graphql.operation.name` | The name of the operation. Absent for an anonymous operation.
| Status | `ERROR` when the execution failed or its result has an error. Each GraphQL error of the result is recorded as an `exception` event with `exception.type` (the error classification) and `exception.message`.
|===

The module does not record the query text (`graphql.document`): it can hold values that must not reach a trace backend.

=== The request span is current

The request span is current on the thread that runs the operation and in the propagated context of the execution, the Micronaut `PropagatedContext` that the library restores after an async field. A span that your code starts while it resolves a field is a child of the request span, and so is an HTTP client call or a JDBC call. That holds for a resolver that runs after a `CompletionStage` completes, and for a batch loader that runs when the DataLoader dispatches. A method annotated with `@NewSpan` is the usual way to start one, see <<resolverSpans>>.

=== Fields

No field has a span unless you select it. `micronaut.graphql.tools.tracing.fields` is a list of `Type.field` and `Type.*` entries, naming fields of object types:

[source,yaml]
----
micronaut:
  graphql:
    tools:
      tracing:
        fields:
          - Query.searchProfile
          - Mutation.*
----

The selection is a `FieldFetcherDecorator`, which the library asks once for each field at startup, never per request. The decorator wraps the fetcher of a selected field in a span named `Type.field`, a child of the request span, current while the fetcher runs and ended when the value is there (for a field that returns a future, when the future completes). It records the attributes `graphql.field.name` and `graphql.field.path`, the names that the OpenTelemetry GraphQL instrumentation uses. A field that the selection excludes gets back the very fetcher it was offered: it has no span and no instrumenter call, and costs nothing. Two kinds of field never get a span, even when selected, because a span there would only measure noise or nothing:

* A property read (a field the library serves from a property of its Java type): it is a trivial fetcher, and the library does not offer it to the decorator.
* A field of the subscription type, whose value is a stream.

An entry that names no type or no field fails the startup with a message that names the key `micronaut.graphql.tools.tracing.fields`.

=== Spans for your own resolvers

The module does not need a span for each resolver of its own: a resolver is a Micronaut bean, and Micronaut Tracing gives a bean method a span with an annotation. `@NewSpan` starts a span for a call, `@ContinueSpan` adds to the span that is current (the field span, when you selected the field, else the request span), and `@SpanTag` puts an argument on the span as an attribute. All three are in `io.micronaut.tracing.annotation`, and they need `micronaut-tracing-opentelemetry` on the runtime classpath. Because the request span is current, the span of an annotated resolver method is a child of it, and a span that it starts is a child of its own.

The annotation needs no support from this library, and it works on a resolver of every language the library supports. A Kotlin class and its methods are `open` (the `allopen` plugin that the Micronaut Gradle plugin applies opens a `@Singleton`). A Groovy class needs the Micronaut AST transform, which `micronaut-inject-groovy` provides. A method that the application does not own, or that you want to trace without an annotation, is a candidate for `micronaut.graphql.tools.tracing.fields` instead.

=== Why the module has its own instrumenter

OpenTelemetry publishes `opentelemetry-graphql-java` (`GraphQLTelemetry`), an alpha artifact, which also instruments graphql-java. The module does not use it. It overrides `instrumentDataFetcher`, so graphql-java wraps every field of every request in a lambda that keeps the context current, even when no field span is wanted, which gives up the per-field cost guarantee of <<cost>>. It has no way to select fields, and it is not a stable API.

[[cost]]
== Cost

With the modules on and no field selected, a request adds a constant cost (a timer, a span and a small state object), and no cost per field: the instrumentation implements no field hook, and no data fetcher is replaced. The allocation gate of the benchmarks (`observedInvocationSlope`) keeps this: the bytes per field of a request with both modules on equal those of the same request with an `Instrumentation` bean that implements no hook, on every graphql-java leg. One thing is graphql-java's, not the module's: graphql-java 21 chains any `Instrumentation` with its own, and that chain allocates for each field (about 550 bytes) whatever the instrumentation does. graphql-java 22 and later do not. If a request of many fields matters more to you than the metrics, stay on graphql-java 22 or later.

A selected field pays for its span (a cost of the OpenTelemetry module only; the field-wrapping code is in no other module): one `Instrumenter` call, a propagated-context scope and a few allocations for each call. The `benchmarks` module measures it next to the cost of a decorator that does nothing.

== Configuration

[cols="3,2,5", options="header"]
|===
| Key | Default | Meaning
| `micronaut.metrics.binders.graphql.enabled` | `true` | Turns the GraphQL metrics off. `micronaut.metrics.enabled=false` turns them off too, with the rest of the Micronaut metrics.
| `micronaut.metrics.binders.graphql.max-operations` | `100` | The most distinct operation names the timer is tagged with.
| `micronaut.graphql.tools.tracing.enabled` | `true` | Turns the tracing off. `micronaut.otel.enabled=false` turns it off too, with the rest of Micronaut Tracing.
| `micronaut.graphql.tools.tracing.fields` | empty | The fields that get a span, as `Type.field` or `Type.*`.
| `micronaut.graphql.tools.tracing.add-operation-name-to-span-name` | `false` | Adds the operation name to the span name of a request: `query GetUser` instead of `query`.
| `micronaut.graphql.tools.execution.data-loader-statistics` | `false` | Counts the batches of each batch loader bean, which the DataLoader meters read.
|===
