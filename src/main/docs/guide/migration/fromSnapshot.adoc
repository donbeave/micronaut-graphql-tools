This page is for applications built on `1.0.0-SNAPSHOT`. No release was published before `1.0.0-M1`, so no published API breaks here. The changes matter for snapshot builds and for anyone who moves to the milestone releases.

The numbers `BC-01` to `BC-19` are the ones of the 1.0.0-M1 release notes, `BC-20` is the one of the 1.0.0-M2 release notes, `BC-21` is the first of 1.0.0-M3, and `BC-22` to `BC-33` follow it, then the changes of 1.0.0-M4. Other later breaking changes are named by their issue number until they get a number. Each change is either on `master` now or marked _pending_ with the issue that will make it.

Changes BC-01, BC-02, BC-04, BC-05, BC-06, BC-10, BC-11, BC-13, BC-15 and BC-17 have no opt-out. There is no legacy mode and no warning period for them. Each startup failure names its fix in the message.

Snippets are Java. The same changes apply to Kotlin and Groovy classes.

== Entries for 1.0.0-M1

=== BC-01: `List<CompletionStage<T>>` is a startup error

Before, a field whose return type was a list of futures was accepted, and the client received the future's `toString()`. Now the startup fails with `[unsupported-return-type]`. The message names the fix: return `CompletionStage<List<T>>`, for example by combining the element futures with `CompletableFuture.allOf`, or load the elements with a DataLoader.

Status: approved, no opt-out.

[source,java]
----
// Before: accepted, and the client received the future's toString()
public List<CompletionStage<Author>> authors(Book book) { ... }

// After: one future for the whole list
public CompletionStage<List<Author>> authors(Book book) { ... }
----

=== BC-02: wrappers and `Optional` placement

Before this change, only `CompletionStage` was unwrapped. Most of the shapes below therefore already failed at startup, with a different message. The change is the message, and three shapes that now work:

* `Optional<T>` on a nullable field or on each element of a nullable list (an empty `Optional` becomes `null`);
* `DataFetcherResult<T>` on a field or on each list element;
* `Publisher<T>` on a field of the subscription type;
* `Mono<T>` on any other field, and `Flux<T>` on a list field (since 1.0.0-M4, #75: the library subscribes and adapts it to a `CompletionStage`).

These shapes fail at startup with `[unsupported-return-type]`:

* `Optional<T>` on a non-null GraphQL type, such as `String!` or `[String!]`;
* wrappers in the wrong order or repeated;
* a `Publisher` of many values (`Flux`) on a field that is not a list, a `Publisher` inside a list or inside a `CompletionStage`, and a `Publisher` on a bean property;
* a subscription field that does not return a `Publisher`, optionally inside a `CompletionStage`.

Status: approved, no opt-out.

[source,java]
----
// Schema: nickname: String!
// Before and after: fails at startup, Optional is not allowed for a non-null type
public Optional<String> nickname(User user) { ... }

// Fix: make the GraphQL field nullable (nickname: String), or return the value itself
public String nickname(User user) { ... }

// Flux on a query field that is not a list fails at startup
public Flux<String> greeting() { ... }

// Fix: return a Mono (or a CompletionStage), or make the field a list
public Mono<String> greeting() {
    return Mono.just("hello");
}
----

=== BC-03: build, POM and publishing

Before, the build required Java 21, and the published POM declared extended-scalars 21.0 (it was 20.2 before).

Now the library compiles to Java 17 bytecode (`--release 17`). The project's CI builds it on JDK 21 and 25. Nothing is published to Maven Central or to a snapshot repository.

Status: not covered by #79; the release notes list it.

Fix: run the library on Java 17 or newer. Build the full project, including `graphql-tools-processor`, on JDK 21 or newer; on JDK 17 only the library module can be checked. To use the library, build and publish it to a local or private repository. If you pin `graphql-java-extended-scalars`, pin the version your build resolves: check it with `./gradlew dependencies`.

=== BC-04: `@Inherited` resolver stereotypes

`@GraphQLRootResolver` and `@GraphQLTypeResolver` are `@Inherited`. A bean that extends an annotated class is a resolver too. The subclass cannot remove an inherited annotation, so a fake or a subclass that is also a bean can bind the same field as the original and create an ambiguity.

Fix: annotate the fake or the subclass with `@Replaces(<original>.class)`. A `@Requires(env = "test")` alone does not help: both beans are active in the test environment. To add behaviour around a resolver, use a Micronaut AOP interceptor, not a subclass bean.

Status: approved, no opt-out. #73 (M4, BC-34) removed the bean stereotype from the annotations, so a class that only inherits one is no bean. A `@Singleton` subclass of an implementation stays a second resolver, so `@Replaces` stays the fix.

[source,java]
----
@GraphQLTypeResolver(Book.class)
@Singleton
public class BookLabelResolver {
    public String label(Book book) { ... }
}

// Fake for the tests: replaces the original bean instead of competing with it
@Replaces(BookLabelResolver.class)
@Singleton
public class FakeBookLabelResolver extends BookLabelResolver {
    @Override
    public String label(Book book) { return "test label"; }
}
----

=== BC-05: getters that only the implementation declares

An object type mapped to a Java interface that has its own introspection reads its properties through that introspection. A getter that only an implementation class declares does not bind any more. Before, it bound silently. Now the startup fails with `[field-not-bound]`, which names the interface, the implementation that declares the getter, and the fix.

Fix: declare the getter on the interface. Removing the interface's own introspection (the `@GraphQLType` or `@Introspected` annotation on the interface) is not a complete fix in strict mode, so declare the getter.

Status: approved, no opt-out.

[source,java]
----
@Introspected
public interface Book {
    String getTitle();

    // Before: declared only in BookImpl, it bound silently. Now: declare it here.
    String getSummary();
}
----

=== BC-06: member mapped outside the declared Java type

A union member or an interface implementation that is mapped to a Java type which cannot be the field's declared Java interface fails the startup with `[incorrect-member-mapping]`. The check is narrowed: only provably disjoint pairs fail, that is a `final` class that does not implement the interface, or classes that are unrelated. Other mappings are accepted.

Fix: map the member to a class that matches the field's declared Java interface.

[source,java]
----
public interface Coded {
    String getCode();
}

// Before: Stray is final and does not implement Coded, so no object can be both.
// Startup fails with [incorrect-member-mapping].
public final class Stray {
    public String getCode() { return "stray"; }
}

// After: Stray implements the Java interface that the field declares
public class Stray implements Coded {
    @Override
    public String getCode() { return "stray"; }
}
----

Status: approved, no opt-out; narrowed to provably disjoint mappings.

=== BC-07: `UnionTypeResolver` renamed to `AbstractTypeResolver`

The public class `UnionTypeResolver` is renamed to `AbstractTypeResolver`, in package `io.micronaut.graphql.tools.internal.resolver`. Dictionary error messages changed too.

Fix: rename the type in imports and in every reference.

[source,java]
----
// Before
import io.micronaut.graphql.tools.schema.UnionTypeResolver;

// After
import io.micronaut.graphql.tools.internal.resolver.AbstractTypeResolver;
----

=== BC-08: input class properties

Two checks are startup errors now:

* A property of an input class that the GraphQL input type does not define. It can be set by a setter or the constructor, but no request can set it. Strict mode fails the startup for these, in one `[unmapped-input-property]`.
* An input field that the input class cannot set. This fails with `[input-field-not-settable]` and has no opt-out.

Opt-out for the first check: `micronaut.graphql.tools.checks.unmapped-input-property` set to `warn` or `ignore` accepts these properties. Setting `strict: false` also accepts them, with a warning. The second check has no opt-out.

Fix: add the field to the input type, or remove the property. Make the field settable with a setter or the constructor.

Status: the unmapped-property check has an opt-out, the unsettable field has none.

[source,java]
----
// Schema: input CreateBook { title: String! }
// Fails at startup in strict mode: the input type does not define isbn
@GraphQLInput
public class CreateBook {
    private String title;
    private String isbn;

    // getters and setters for title and isbn
}

// Fix: add `isbn: String` to the input type, or remove the property
----

=== BC-09: primitive for a nullable built-in scalar

In strict mode, an argument or an input class property declared as a primitive (`int`, `boolean`, `double`, ...) for a nullable built-in scalar (`Int`, `Boolean`, `Float`, `Long`, ...) fails the startup with `[nullable-primitive]`. A `null` cannot reach a primitive, so the value would be the primitive's default.

Fix: use the wrapper class, or make the GraphQL type non-null.

Opt-out: `micronaut.graphql.tools.checks.nullable-primitive` set to `warn` or `ignore` (`strict: false` is `warn` for every check).

[source,java]
----
// Schema: quantity: Int (nullable). Fails in strict mode.
public Book reserve(int quantity) { ... }

// Fix: the wrapper class
public Book reserve(Integer quantity) { ... }
----

=== BC-10: the `GraphQL` bean is created only when there is none

The library creates its `GraphQL` bean only when the application does not define one. The `GraphQLSchema` bean is exposed, so the application can use it. The schema is still bound at startup, so a broken binding fails the startup even when the application defines its own `GraphQL` bean.

Which application bean makes the library step aside: the library's `GraphQL` and `GraphQLSchema` beans step aside only for an application bean of the same type that has no qualifier, or that is `@Primary`. A bean with a qualifier, such as `@Named("admin")`, is a secondary bean that is injected by its qualifier. It does not replace the library's bean, and the library's beans are `@Primary`, so an unqualified injection point still gets them. A bean registered at runtime counts like any other. A bean that an enabled `@Replaces` bean replaces does not count (the `bean`, `factory` and `named` members are matched; the `qualifier` member is not evaluated, so a bean replaced that way still counts), and an `@EachProperty` or `@EachBean` template counts by the beans it expands to: named expansions do not replace the library's bean, an expansion that is unqualified or primary does. When the application provides its own `GraphQLSchema` bean, the library binds nothing, and the `BindingManifest` bean fails with a message that names that bean. At startup the library logs at INFO which `GraphQL` and `GraphQLSchema` beans are in use and why the library's bean was or was not created (logger `io.micronaut.graphql.tools.internal.BeanSelectionLogger`).

Fix: to change the library's `GraphQL` without replacing it, add a `GraphQLBuilderCustomizer`. To replace it, define your own `GraphQL` bean.

Status: approved, no opt-out.

[source,java]
----
@Singleton
public class GraphQLTuning implements GraphQLBuilderCustomizer {
    @Override
    public void customize(GraphQL.Builder builder) {
        // change the builder the library uses
    }
}
----

=== BC-11: a bare `SchemaDirectiveWiring` bean

A `SchemaDirectiveWiring` bean that no `SchemaDirective` bean wraps was ignored before. It is a startup error now, `[unwrapped-directive-wiring]`. The message names the two wrappers.

Fix: wrap the wiring. Use `SchemaDirective.named(name, wiring)` for one directive. Use `SchemaDirective.everyElement(names, wiring)` only for a wiring that must see every schema element: graphql-java calls it for each element, so it must check the directives itself.

Status: approved, no opt-out.

[source,java]
----
// Before: a bare bean, ignored
@Singleton
public class AuthWiring implements SchemaDirectiveWiring { ... }

// After: wrapped in a SchemaDirective bean, produced by a factory
@Factory
public class AuthDirectives {
    @Singleton
    SchemaDirective authDirective(AuthWiring wiring) {
        return SchemaDirective.named("auth", wiring);
    }
}
----

=== BC-12: directives without a wiring

A directive that the schema applies without a wiring is a startup error, `[unwired-directive]`, which lists where each one is applied. A wiring is a `SchemaDirective` bean, a `RuntimeWiringCustomizer` that registers a wiring under the directive's name, or a name in `resolver-directives`. graphql-java's built-in directives need none.

Opt-out: `allow.inert-directives` lists the names. With `checks.unwired-directive: warn` (or `strict: false`) the startup logs one warning that lists them, and the schema keeps the directives without effect. `ignore` skips the check.

Status: opt-out exists.

[source,yaml]
----
micronaut:

    tools:
      allow:
        inert-directives:
          - deprecated-since

=== BC-13: a `RuntimeWiringCustomizer` that replaces the library's wiring

A `RuntimeWiringCustomizer` may only add to the runtime wiring. One that replaces the library's wiring fails with `[runtime-wiring-override]`. On graphql-java 25 the builder rejects the first replaced default data fetcher, type resolver or scalar itself, with `StrictModeWiringException`, so the startup fails with that exception instead. A replaced data fetcher of a library-wired field is always reported as `[runtime-wiring-override]`.

Fix: add to the library's wiring in the customizer. To serve a field with a hand-written `DataFetcher`, return its coordinate from `claimedFields()`. The library then does not bind the field. The library does not traverse the return type of a claimed field, so that type must also be reached through another bound field, or listed in `allow.unreachable`.

Status: approved, no opt-out. `claimedFields()` is on `master`.

[source,java]
----
@Singleton
public class BookFetcherCustomizer implements RuntimeWiringCustomizer {
    @Override
    public void customize(RuntimeWiring.Builder builder) {
        builder.type("Query", type -> type.dataFetcher("latestBook", env -> latestBook()));
    }

    @Override
    public Set<FieldCoordinates> claimedFields() {
        return Set.of(FieldCoordinates.coordinates("Query", "latestBook"));
    }
}
----

=== BC-14: a property and a type resolver bind one field

When a member of the Java type (a property or a `@GraphQLField` method) and a type resolver method can both bind a field, the startup fails with `[precedence-ambiguity]`, which names the field and both members. Before, the property won silently.

[source,java]
----
// Schema: type Book { id: ID! }. The getter and the type resolver method both bind Book.id,
// so startup fails with [precedence-ambiguity].
public class Book {
    public String getId() { return "1"; }
}

@GraphQLTypeResolver(Book.class)
@Singleton
public class BookResolver {
    public String id(Book book) { return book.getId(); }
}

// After: the getter is ignored, so the type resolver method alone binds the field
public class Book {
    @GraphQLIgnore
    public String getId() { return "1"; }
}
----

Fix: remove one of the two members. Or choose the winner: set `micronaut.graphql.tools.precedence` to `property-first` (the old behaviour) or `resolver-first`, or mark the field with a schema directive that is listed in `resolver-directives`, so that the type resolver method binds it. A getter can also carry `@GraphQLIgnore`, so the type resolver binds the field without an ambiguity.

Opt-out: `micronaut.graphql.tools.precedence: property-first`. `strict: false` does not change this outcome.

The default value of `precedence` is named `fail` (BC-29). The behaviour of the options above is unchanged.

[source,yaml]
----
micronaut:
  graphql:
    tools:
      precedence: resolver-first
----

=== BC-15: root resolvers per operation type

Root resolver methods are scoped to one root operation type (`Query`, `Mutation` or `Subscription`). Before, the first bean found won when two root methods bound one field. Now two root methods for one field are a startup error, `[multiple-methods-found]`. A method without a coordinate binds the field of its name on every root operation type. Strict mode also fails on a method without a coordinate that binds the same field name on several operation types.

Fix: when the methods serve different operation types, give each one its own coordinate, for example `Query.ping` and `Mutation.ping`. Two methods with the same coordinate still conflict, so remove one of them. When one bean is meant to override another, annotate the overriding bean with `@Replaces`.

Status: approved, no opt-out.

[source,java]
----
@GraphQLRootResolver
public class PingQuery {
    @GraphQLSchemaCoordinate("Query.ping")
    public String ping() { return "pong"; }
}

@GraphQLRootResolver
public class PingMutation {
    @GraphQLSchemaCoordinate("Mutation.ping")
    public String ping() { return "pong"; }
}

// A test fake that overrides PingQuery: @Replaces drops the original bean, so only the fake binds Query.ping
@Replaces(PingQuery.class)
@GraphQLRootResolver
public class FakePingQuery extends PingQuery {
    @Override
    @GraphQLSchemaCoordinate("Query.ping")
    public String ping() { return "test pong"; }
}

=== BC-16: strict mode is on by default

`micronaut.graphql.tools.strict` defaults to `true`. Strict mode fails the startup on bindings that work but are probably mistakes: stale resolver methods, Java enum constants without a schema value, dictionary entries for types that are not bound, interface-mapped types without their own introspection, unused enum, input and scalar types, and the other findings that the strict mode checks in the README list. Most findings are also a `!` line of the binding manifest. Some have no manifest line, for example interface-mapped types without their own introspection, and primitives for nullable built-in scalars; the startup exception is their only report.

=== BC-19: resolver parameters bind by name

Resolver parameters are bound to field arguments by name, not by position. A parameter without an argument of its name, or two parameters bound to one argument, fails the startup with `[argument-mismatch]`.

Fix: rename the parameter to the argument name, or add `@GraphQLArgument("<argument name>")`.

Status: breaking by design; no opt-out. The runtime half is on `master` (PR #257). The compile-time visitor of `graphql-tools-processor` applies the same rule (#15), with the same code and coordinate. #291 registers the visitor in a build, so a misnamed or missing parameter fails the compilation.

A parameter of a method inherited from a class file that carries no parameter names (built without `-parameters`, or without `-g` for a method with a body) has the name `arg0`. The failure then says to compile the class that declares the method with `-parameters`, or to add `@GraphQLArgument`. The guide page "Inputs" lists where the names come from.

[source,java]
----
// Schema: book(id: ID!): Book
// Before: bound by position. Now: fails, there is no argument named isbn.
public Book book(String isbn) { ... }

// Fix: rename the parameter
public Book book(String id) { ... }

// Or keep the name and bind the argument explicitly
public Book book(@GraphQLArgument("id") String isbn) { ... }
----

== Entries for 1.0.0-M3

=== BC-21: enums need a bean introspection (#33)

The library wires one values provider per bound enum, built at startup from the enum's bean introspection (`EnumBeanIntrospection`, generated at compile time). graphql-java then coerces an enum argument, an enum input field and an enum default value to the Java constant itself, so the resolver receives it without a conversion call. The library no longer reads enum constants by reflection (`Class#getEnumConstants()`). An enum without a bean introspection fails the startup with `[class-not-introspected]`, which names the class and the annotation to add.

Fix: annotate each Java enum that a field, argument or input field uses with `@Introspected`. Micronaut Serialization's `@Serdeable` also introspects the enum. The compile-time processor does not check this yet.

A `RuntimeWiringCustomizer` that registers its own `enumValues` provider for a bound enum now fails the startup with `[runtime-wiring-override]`, like any other replacement of the library's wiring.

[source,java]
----
// Before: accepted, the resolver received the constant through a conversion of the enum name
public enum Color { RED, GREEN }

// After: bean introspection generated at compile time
@Introspected
public enum Color { RED, GREEN }
----

=== BC-22: one code system for checks and errors (#237)

Every strict check, every startup failure and every compile-time diagnostic has one code, from the `BindingCode` enum of `graphql-tools-binding`. The code is the same token in four places: the `[code]` at the start of the message, `SchemaBindingException#getCode()`, the word after `!` in a binding manifest line, and the check name that `checks.<code>` and `allow.findings` use. The list is in the error reference.

What breaks for code that read the old forms:

* Every startup exception extends the new public `SchemaBindingException`, and its message starts with `[code] `. A test that compares a whole message, or that checks `startsWith`, needs the prefix. A test that checks `contains` is not affected.
* The manifest `!` lines changed their first word, as the summary table lists. Code that reads `!unbound`, `!unusedDictionary`, `!ambiguous`, `!unreachable` or `!unwiredDirective` lines reads the codes now.
* The failures that gather several (`[binding-failures]` and `[strict-findings]`) tag each finding with its own code. `SchemaBindingException#getCodes()` returns the check code of each strict finding, and `getFailures()` lists the failures of `[binding-failures]`.

Fix: match on `exception.getCode()` (or on the `[code]` token), and read the manifest kinds from the table in the error reference.

[source,java]
----
try {
    applicationContext.getBean(GraphQL.class);
} catch (BeanInstantiationException e) {
    if (e.getCause() instanceof SchemaBindingException failure
            && failure.getCode() == BindingCode.UNBOUND_ENUM_CONSTANT) {
        // ...
    }
}
----

=== BC-23: arguments and input objects are converted from `BeanIntrospection` (#37)

Before, every list, input object and enum argument went through Jackson's `convertValue` on each request. Now the library builds one converter per argument and per input type at startup, from the declared type and from the bean introspection that Micronaut generated at compile time, and a request runs no Jackson and no reflection. Instances are built through the introspected constructor, then the remaining input fields are set through their `BeanProperty`; a field the client leaves out is not set, and an `ArgumentValue` is set to `omitted()` from the keys of the coerced map, in the same pass.

What stops being the input contract:

* Jackson annotations on an input class (`@JsonIgnore`, `@JsonProperty`, `@JsonCreator`, `@JsonDeserialize`) and the naming strategy of an `ObjectMapper`. An input field is bound to the property or constructor parameter of the same name.
* `FAIL_ON_UNKNOWN_PROPERTIES` and every other `ObjectMapper` setting. An `ObjectMapper` bean, whatever its name, is not read. The `INPUT_OBJECT_MAPPER` constant is removed.
* A list argument or input field is converted into `List`, `Collection`, `Iterable` (an `ArrayList`), `Set` (a `LinkedHashSet`), `SortedSet` (a `TreeSet`), `Deque` or `Queue` (a `LinkedList`). Any other declared collection fails the startup with `[unsupported-input-type]`.
* `[input-field-not-settable]` now says that the property has no setter and no constructor parameter. A property with an `ArgumentValue` type may be write-only, and an `ArgumentValue` property that an input type does not define is set to `omitted()`.

Fix: name the properties and the constructor parameters of an input class like the input fields. Put a `TypeConverter<Map, SomeInput>` bean in the application for an input class that needs a conversion of its own (the bean builds the whole instance, `ArgumentValue` properties included), and a `GraphQLScalarMapping` for a custom scalar. A scalar value that is not an instance of the declared class goes through the Micronaut `ConversionService`, which holds the application's `TypeConverter` beans.

[source,java]
----
// Before: Jackson read the annotation, and the field "legacy_code" bound to "legacyCode"
@GraphQLInput
public class ItemInput {
    @JsonProperty("legacy_code")
    private String legacyCode;
}

// After: the property carries the name of the input field
@GraphQLInput
public class ItemInput {
    private String legacyCode;
    // getter and setter, or a constructor parameter named legacyCode
}
----

=== BC-25: the binding manifest has a specified format, version 2 (#90)

The manifest format is specified on the "Binding Manifest" page and its version is the number on the first line. Version 2 differs from version 1 in four ways:

* The separators are ASCII: ` -> ` replaces the arrow and ` ; ` replaces the middle dot, in entries and in findings. The text is ASCII only: a character outside `0x20` to `0x7e` and the backslash in a part are written `\uXXXX`. A part that holds a line break is escaped instead of failing the rendering.
* A `scalar` line names the scalar in the member part (`Long -> scalar ; Long ; - ; -`). It named the `Coercing` class (`graphql.scalars.java.JavaPrimitives$1`), which could be an anonymous class and changed with the graphql-java version. A `claimed` line names the customizer by a class a reader can find, never an anonymous or generated class.
* The schema hash is computed over the definitions sorted by name, with the extensions of a name sorted by their printed text. The same schema files loaded in any order give one hash. The hash of every schema differs from the hash of version 1.
* The first line is `# graphql-binding-manifest 2`.

Fix: regenerate every checked-in manifest, and change a reader that splits lines on the arrow or the middle dot to split on ` -> ` and ` ; `. A reader should check the version on the first line and refuse a version it does not know. The manifest of the startup is written in version 2.

=== BC-26: Jackson leaves the `api` scope (#36)

The library's `api` scope brought `micronaut-jackson-databind` to every application. The library itself does not use Jackson (#37, BC-23), so the dependency leaves the `api` scope and the library no longer declares Jackson at compile or runtime. An application that gets its JSON from Jackson declares `micronaut-jackson-databind` itself. An application that uses Micronaut Serialization declares `micronaut-serde-jackson` (or another Serde JSON module). Without any JSON codec, an application that serves HTTP fails at startup with `No bean of type [io.micronaut.json.JsonConfiguration] exists`.

=== BC-27: per-check severity and removed keys (#86)

Each of the ten checks has a severity, set with `micronaut.graphql.tools.checks.<code>`: `fail` (the default of every check), `warn` (log the finding and go on) or `ignore` (skip the check; it does no work). `strict` is the shorthand for the checks without an entry: `true` leaves them at `fail`, `false` makes them `warn`. `unreachable-type` is split into two codes: `unreachable-type` for object, interface and union types, and `unreachable-value-type` for enum, input and scalar types. `strict: false` now also warns on unreachable object, interface and union types, which failed before. `precedence` does not depend on `strict`.

What breaks:

* Six keys are removed, with no alias (`input.detect-omission` of BC-28 fails the same way). If one is set, the startup fails with `[removed-configuration-key]` and names the replacement:

[cols="2,3", options="header"]
|===
| Removed key | Replacement
| `micronaut.graphql.tools.unreachable-types` | `micronaut.graphql.tools.checks.unreachable-type` and `micronaut.graphql.tools.checks.unreachable-value-type` (the old `ignore` is `warn`)
| `micronaut.graphql.tools.input.unmapped-properties` | `micronaut.graphql.tools.checks.unmapped-input-property`
| `micronaut.graphql.tools.allow-unreachable` | `micronaut.graphql.tools.allow.unreachable`
| `micronaut.graphql.tools.inert-directives` | `micronaut.graphql.tools.allow.inert-directives`
| `micronaut.graphql.tools.schema-customizer-directives` | `micronaut.graphql.tools.allow.schema-customizer-directives`
| `micronaut.graphql.tools.unwired-directives` | `micronaut.graphql.tools.checks.unwired-directive`
|===

* An unknown check code or a severity other than `fail`, `warn` or `ignore` fails the startup with `[invalid-check-setting]`.
* A check at `ignore` writes no `!` line to the binding manifest. The checks `root-method-several-operations`, `interface-read-through-implementation` and `nullable-primitive` now write `!` lines too.
* A primitive for a nullable built-in scalar fails with the code `nullable-primitive` (was `incorrect-class-mapping`).
* Three new codes: `invalid-check-setting`, `removed-configuration-key` and `invalid-allow-findings`.

New: `allow.findings` takes lines of the binding manifest, exactly as the manifest writes them (`!unbound-resolver-method example.Query#helper(java.lang.String)`), and accepts exactly that finding. An entry that is not the line of a check, whose check is `ignore`, or that matches no finding fails the startup. `allow.unreachable`, `allow.inert-directives` and `allow.schema-customizer-directives` are validated as before.

=== BC-28: `ArgumentValue` needs no option (#159)

`micronaut.graphql.tools.input.detect-omission` (default `false`) was a second opt-in next to the declared `ArgumentValue` type: with the option off, an `ArgumentValue` parameter or property failed the startup. The option is removed. The converter of an input type handles omission when the type has an `ArgumentValue` property or constructor parameter, and a type without one pays nothing.

* A configuration key `micronaut.graphql.tools.input.detect-omission` fails the startup with `[removed-configuration-key]`, which says to declare `ArgumentValue` on the resolver parameter or the input property.
* The compile-time option `-Amicronaut.graphql.tools.input.detectOmission` fails the compilation as an unknown option under the `micronaut.graphql.tools.` prefix.

=== BC-29: one precedence rule for object and interface fields (#105)

A field can be bound by a member of its Java type (a property or a `@GraphQLField` method) and by a type resolver method (of the type, or of an interface that declares the field). One rule decides it, for object and interface fields alike, at startup and in the compile-time checks that apply it:

. A member marked `@GraphQLIgnore` is no member, so the type resolver method binds the field.
. A field that carries a directive listed in `resolver-directives`, or whose type resolver method declares its coordinate with `@GraphQLSchemaCoordinate`, is bound by the type resolver method. Nothing is logged.
. Any other ambiguity follows `micronaut.graphql.tools.precedence`: `fail` (the default) fails the startup with `[precedence-ambiguity]`, `resolver-first` binds the resolver method and `property-first` binds the member; both log the ambiguity at WARN and write a `!precedence-ambiguity` line to the manifest.

`precedence` does not depend on `strict`, and it is not a `checks.<code>` entry. `property-first` stays through 1.0.

What breaks:

* The value `strict` is renamed `fail`, and `strict` is rejected: the startup fails with `[removed-configuration-key]` that names `fail`. The default does not change.
* A type resolver method that declares its coordinate now wins over a member of the same field. Before, with the default it was an ambiguity, and with `property-first` the startup failed with `[unknown-schema-coordinate]` because the property bound the field.

The Relay `Node.id` case is written with the coordinate on the interface resolver, so an entity keeps its own `getId()`:

[source,java]
----
@GraphQLTypeResolver(Node.class)
public class NodeResolver {
    @GraphQLSchemaCoordinate("Node.id")
    public String id(Node node) { return globalId(node); }
}
----

Fix: write `precedence: fail` or delete the line. The error message names the options for one field (a resolver directive, `@GraphQLSchemaCoordinate`, `@GraphQLIgnore`) and for every field (`precedence: resolver-first` or `property-first`).

=== BC-30: a smaller public API (#109)

Startup failures are one public class, `SchemaBindingException`, with a stable error code from `BindingCode`. Every code is listed in the error reference, and the code tables of that page are generated from the enum. Before, 43 subclasses in `io.micronaut.graphql.tools.exceptions` were public, one for each kind of failure. They are internal now (`io.micronaut.graphql.tools.internal.exceptions`) and can change in any release.

What breaks:

* Code that catches or tests a subclass (`catch (MethodNotFoundException e)`, `e.getCause() instanceof UnwiredDirectivesException`, a Spock `thrown(AmbiguousBindingException)`) no longer compiles: the classes are not in the API package any more.
* Code that read the data of one subclass (`getProblems()`, `getTypeNames()`, `getMembers()`, `getUnwiredDirectives()`, `getMissingValues()`, `getProvidedCount()` and so on) cannot. The same text is in the message, which names the coordinate, the Java element and the way out. `AbstractMappingException#getMappingContext()` is `SchemaBindingException#getMappingContext()`, which is `null` for a failure that is about no single element, and `BindingFailuresException#getFailures()` and `StrictModeException#getCodes()` are `SchemaBindingException#getFailures()` and `getCodes()`.

* The types of `io.micronaut.graphql.tools` that were annotated `@Internal` moved to `io.micronaut.graphql.tools.internal`: the factories, the resolvers registry, the runtime wiring generator, the binding manifest recording and the rest. `io.micronaut.graphql.tools.processor` (the runtime method processors, not the compile-time module) is now `io.micronaut.graphql.tools.internal.registry`. They were never API, but a few were `public`: an import of one of them, or a logger setting that names one by its full name, must change. The package `io.micronaut.graphql.tools` holds public API only.

Fix: match on the code, and on the coordinate if the failure is about one schema element. Do not import from a package named `internal`.

[source,java]
----
try {
    applicationContext.getBean(GraphQLSchema.class);
} catch (BeanInstantiationException e) {
    if (e.getCause() instanceof SchemaBindingException failure
            && failure.getCode() == BindingCode.PRECEDENCE_AMBIGUITY) {
        log.error("{} binds twice", failure.getCoordinate());
    }
}
----

=== BC-31: role packages for the public API (#354)

The public types that shared the root package `io.micronaut.graphql.tools` moved into packages named by their role. Only the package changed: the class names, members, bean names and the configuration keys (`micronaut.graphql.tools.*`) are the same.

[cols="2,3", options="header"]
|===

== Pending changes

The following changes are planned and are not on `master` yet. Their behaviour is not described as current. Each entry names the issue that makes the change.


=== BC-24: schema files are `*.graphqls` (#17)

The runtime finds the schema files itself (`micronaut.graphql.tools.schema.locations`, default `classpath:graphql/**/*.graphqls`), and the compile-time processor reads the same files with the same code. Both read `*.graphqls` only, so a client operation file (`*.graphql`) in the schema directory is not a schema file and cannot break the build. Before, the processor read every `*.graphql` file as schema.

Rename the schema files that end in `.graphql` to `.graphqls`. A `TypeDefinitionRegistry` bean of your own still replaces the discovery, and a schema without a `schema { }` block and with a `Query` type now binds with `Query`, `Mutation` and `Subscription` as roots.

=== BC-32: compile-time options renamed (#291)

The visitor replaces the earlier annotation processor of `graphql-tools-processor`. #291 registers the visitor, removes the processor's service files, and renames the options; #144 deletes the processor's classes from the jar:

* `micronaut.graphql.tools.sdlDir` is replaced by `micronaut.graphql.tools.processor.schema.dirs`;
* `micronaut.graphql.tools.processor.checks` (`true` by default) switches the compile-time checks off when it is `false`;
* `micronaut.graphql.tools.processor.module.dir` (optional) is the project directory of the module that sets `schema.dirs`; it makes a `schema.dirs` left behind by an earlier module of the same JVM fail the build instead of being used.

A build that passes `micronaut.graphql.tools.sdlDir` fails with `[processor-option-removed]` and the name of the replacement.

The build no longer writes `binding-manifest.txt`, `binding-manifest-omitted.txt` or `accessors.txt` into the class output (the startup writes the manifest, and a build guard that checks for the file must go), and the member of a property in the manifest is written `Class#property`, not `Class#getProperty()`. Regenerate a checked-in manifest.

A misnamed or missing resolver parameter now fails the build with `[argument-mismatch]` (#15). `[class-not-introspected]` stays a compile-time warning, since an `@Introspected(classes = ...)` declaration in another class can make the class introspected; a build with `-Werror` fails on the warning.

Status: breaking by design; no opt-out.

=== BC-33: inherited type resolver contracts are recorded at compile time (#34)

The startup used to read `@GraphQLTypeResolver` from the class hierarchy of each type resolver bean with `Class.getDeclaredAnnotation`, which needs reflection metadata in a native image and returns a JDK annotation proxy. Now the visitor of `graphql-tools-processor` walks the superclasses and interfaces of the bean class and writes the contracts into the annotation metadata of the bean, and the registry reads them from the bean definition: no reflection, and the same binding on the JVM and in a native image. The visitor writes them also with `micronaut.graphql.tools.processor.checks=false`.

What breaks: a build that does not run the processor, with a bean that is a type resolver only through an inherited annotation, fails the startup with `[type-resolver-contracts-not-found]`. Before, this worked on the JVM. The message names the processor and where to add it.

Fix: put `micronaut-graphql-tools-processor` on the path of the compiler as the compile-time checks section of the README shows for each tool (`annotationProcessor`, `ksp` or `kapt`, `compileOnly`), or annotate the bean class directly. A bean annotated directly binds without the processor.

Status: breaking by design; no opt-out.

=== BC-34: resolver stereotypes carry no bean (#73)

`@GraphQLRootResolver` and `@GraphQLTypeResolver` carried the `@Bean` and `@DefaultScope(Singleton)` stereotype, so a class that carried one, or extended a class that carried one (the annotations are `@Inherited`), was a singleton bean without a scope annotation. That is what let a fake or a decorator that extends a resolver become a second resolver (BC-04). The annotations are now plain markers with `@Executable(processOnStartup = true)`, and a class is a bean only when it has a scope annotation of its own.

The new marker interfaces of the package `io.micronaut.graphql.tools.resolver` (`QueryResolver`, `MutationResolver`, `SubscriptionResolver` and `TypeResolver<T>`) carry no bean stereotype either. They fix the root operation type, give the source type as a type argument, and make only the methods of a contract interface candidates for binding. See <<resolverContracts,Resolver Contracts>>.

What breaks:

* A resolver class that has no scope annotation is not a bean any more, so its fields are not bound and the startup fails with `[field-not-bound]` or `[method-not-found]`, and the compile-time checks skip it. A subclass of an annotated class needs one too.
* `@GraphQLTypeResolver` has a default value, `void`, for the marker `TypeResolver<T>`. A bean that carries the annotation without a class and without a marker still fails the startup with `[incorrect-annotation]`.
* A type resolver bean whose build did not record its contracts binds only when it carries the annotation itself and has no supertype besides `Object`. Every other one fails the startup with `[type-resolver-contracts-not-found]`, which names the processor. Before, a directly annotated bean was also checked with a reflective walk of its supertypes (`Class.isAnnotationPresent`); that read is removed, so the native image needs no reflection metadata for it.

Fix: add `@Singleton` (or another scope annotation) to each resolver class, and `@Replaces(<original>.class)` to a fake or a subclass of a resolver bean:

[source,java]
----
// before: a bean, because the annotation carried the stereotype
@GraphQLRootResolver
public class BookQuery { ... }

// now
@Singleton
@GraphQLRootResolver
public class BookQuery { ... }
----

Status: breaking by design; no opt-out.

== Renaming a binding

Nothing that worked before changes (the new setting is off by default, and the coordinate of a method with another name used to fail the startup, so no application relies on it). Three additions help a migration, see <<renaming,Binding a field to a differently named member>>:

* A resolver named after a getter (`getAuthor(Book)` for the field `author`) binds without renaming with `micronaut.graphql.tools.resolver-accessor-prefixes: true`. A resolver that has both `author` and `getAuthor` for the field then fails the startup with `[multiple-methods-found]`.
* A field named like a Java keyword or an `Object` method (`class`, `default`, `hashCode`) is bound with `@GraphQLField("class")` on a method or a property of the type, or with `@GraphQLSchemaCoordinate("Book.class")` on a resolver method.
* A renamed member binds the new name only; the field of its old name needs another member.

== Migration recipe

To move an application from `1.0.0-SNAPSHOT` in one pass, set these options first. They relax the optional checks and write the binding manifest. They do not relax the changes without an opt-out (BC-01, 02, 04, 05, 06, 10, 11, 13, 15 and 17): the startup still fails for those, and each failure must be fixed as it is reported:

[source,yaml]
----
micronaut:
  graphql:
    tools:
      strict: false
      precedence: resolver-first
      manifest:
        enabled: true
----

`strict: false` makes every check `warn`, including unreachable object, interface and union types, so none of them fails the startup (BC-27).

`resolver-first` is the migration setting, but it is not the snapshot's behaviour. On object types the property used to win silently, so `resolver-first` can return a different value for a field that a property and a type resolver method both bind. Read the ambiguities in the manifest first, or use `precedence: property-first` to keep the old values while you fix them.

Then read the `!` lines of the binding manifest, and fix, annotate with `@GraphQLIgnore`, or allow each one. The compile-time visitor reads `@GraphQLIgnore` and applies the same rules.

When the runtime findings are fixed, add `graphql-tools-processor` to the build. It needs its own build option, `-Amicronaut.graphql.tools.processor.schema.dirs=<directory of the SDL files>` (see the Compile-Time Verification page). It does not read the runtime settings above, and it needs JDK 21 or newer to build.

== Entries for 1.0.0-M4

=== BC-35: resolvers run on the blocking executor by default (#49)

The transport's invocation ran parsing, validation and every synchronous resolver on the thread that received the request, the Netty event loop, so one blocking resolver stalled the server. The library now owns the invocation. Each operation hops once to the executor named by `micronaut.graphql.tools.execution.executor` (default `blocking`) before graphql-java runs. On JDK 21 and later Micronaut maps `blocking` to virtual threads, on JDK 17 to the `io` pool; the library itself makes no call that needs JDK 21.

What breaks: nothing in the schema or the resolvers, but the thread changes. A resolver that read a thread local that is set only on the event loop, or that assumed it runs on the event loop, sees the executor's thread. The propagated context (the request, security and tracing elements of your filters) is installed on the executor thread, so `ServerRequestContext` and `@RequestScope` beans keep working. An application with its own `GraphQLInvocation` declares `@Replaces(DefaultGraphQLInvocation.class)` or `@Primary`; the library then creates none and logs one INFO line.

Status: approved, opt-out with `none`.

[source,yaml]
----
# Before: the event loop. To keep it:
micronaut:
  graphql:
    tools:
      execution:
        executor: none
----

See the Execution page for the executors, the order of the steps and the rejection response.

=== BC-36: a `DataLoaderRegistry` bean fails the startup (#20)

The transport took a `DataLoaderRegistry` bean for each call. A request-scoped registry was then one registry for a whole WebSocket connection, so the loader caches were shared across the operations of that connection, and the lookup failed on any thread that was not the request thread. The library now creates the registry of each execution itself. It holds no loader when it is created: a loader is created from a batch loader bean when a resolver first uses it, and is dropped with the execution.

What breaks: an application with a `DataLoaderRegistry` bean fails the startup with `[data-loader-registry-bean]`, and the message carries the fix. There is no opt-out.

Status: approved, no opt-out.

[source,java]
----
// Before: a registry bean, read by name with an unchecked cast.
@Factory
class Loaders {
    @RequestScope
    DataLoaderRegistry registry(BookSellerLoader loader) {
        return new DataLoaderRegistry().register("sellers", DataLoaderFactory.newMappedDataLoader(loader));
    }
}

DataLoader<String, List<Seller>> loader = environment.getDataLoader("sellers");

// After: the loader is a bean, and the resolver declares the type it needs.
@Singleton
class BookSellerLoader implements MappedBatchLoader<String, List<Seller>> { ... }

CompletionStage<List<Seller>> sellers(Book book, DataLoader<String, List<Seller>> loader) {
    return loader.load(book.getId());
}
----

See the Data Loaders page for the naming rules, the lifecycle and the context contributors.

=== BC-37: unhandled exceptions are hidden from the client (#32)

graphql-java's default handler put the message of every exception into the error: `Exception while fetching data (/stockBoom) : secret detail`. That leaks internals (a SQL fragment, a host name, a constraint name) to any client. The library now installs its own handler. An exception that no mapper handles and that is no `GraphQLError` gets the message `Internal server error` and `extensions.code` `INTERNAL_ERROR`; its message and class go to the log, once, at ERROR and without a stack trace.

What breaks: a client or a test that matched the old message text, and a log alert on the old WARN entries. The path, the locations and the data of the other fields are unchanged.

Status: approved, opt-out for development with `micronaut.graphql.tools.errors.details`, which sends the message and the class. There is no setting that restores the old text format.

[source,yaml]
----
# Before: the message of every exception reached the client. To see it again in development:
micronaut:
  graphql:
    tools:
      errors:
        details: true
----

For production, map the exceptions whose message is meant for the client:

[source,java]
----
@Singleton
class OutOfStockMapper implements GraphQLExceptionMapper<OutOfStockException> {
    @Override
    public GraphQLError map(OutOfStockException exception, GraphQLExceptionContext context) {
        return context.error(exception.getMessage(), Map.of("code", "OUT_OF_STOCK"));
    }
}
----

See the Errors page for the mappers, their order, the details setting and the customizers of the final error list.

=== BC-39: observability follows the Micronaut metrics and tracing conventions (#495)

The observability module recorded metrics and traces under a prefix of its own and called the raw OpenTelemetry API. It now follows the conventions of Micronaut Micrometer and Micronaut Tracing, and its tracing is built on the OpenTelemetry `Instrumenter` API. The module was never released, so the old names have no deprecation period: a key under the old prefix is ignored.

[cols="3,3", options="header"]
|===
| Before | Now
| `micronaut.graphql.tools.observability.enabled` | Removed: use `micronaut.metrics.enabled`, `micronaut.otel.enabled`, or the two keys below
| `micronaut.graphql.tools.observability.metrics.enabled` | `micronaut.metrics.binders.graphql.enabled`
| `micronaut.graphql.tools.observability.metrics.max-operations` | `micronaut.metrics.binders.graphql.max-operations`
| `micronaut.graphql.tools.observability.tracing.enabled` | `micronaut.graphql.tools.tracing.enabled`
| `micronaut.graphql.tools.observability.tracing.fields` | `micronaut.graphql.tools.tracing.fields`, with the same syntax, default and meaning
| none | `micronaut.graphql.tools.tracing.add-operation-name-to-span-name`, `false` by default
|===

What else changes:

* The request span is named after the operation type (`query`, `mutation` or `subscription`), following the OpenTelemetry semantic conventions for GraphQL, because a client chooses the operation name. Before it was `query <operation>`. The attributes `graphql.operation.name` and `graphql.operation.type` are unchanged. A request that does not reach an operation is named `GraphQL Operation`.
* A field span keeps its name `Type.field`. It has `graphql.field.name` and the new `graphql.field.path`; `graphql.field.parent` is removed.
* `GraphQLObservability.PREFIX` and the span attribute constants (`OPERATION_NAME_ATTRIBUTE`, `OPERATION_TYPE_ATTRIBUTE`, `FIELD_PARENT_ATTRIBUTE`, `FIELD_NAME_ATTRIBUTE`) are removed. The meter and tag constants stay.
* The request span is current in the propagated context of the execution. A span that a resolver starts (a `@NewSpan` method, an HTTP client call) is its child; before it was a sibling, a child of the HTTP span.
* The fields that `tracing.fields` selects are chosen by a `FieldFetcherDecorator`, not a `GraphQLSchemaCustomizer`. The same fields get a span, with the same names and parents.

[source,yaml]
----
# Before
micronaut:
  graphql:
    tools:
      observability:
        metrics:
          max-operations: 50
        tracing:
          fields:
            - Query.searchProfile
# Now
micronaut:
  metrics:
    binders:
      graphql:
        max-operations: 50
  graphql:
    tools:
      tracing:
        fields:
          - Query.searchProfile
----

See the observability page for the span layout, `@NewSpan` and `@Timed` on resolvers, and the configuration.

=== BC-40: the scalars configuration is bound to a typed class (#497)

The scalars module read `micronaut.graphql.tools.scalars.<id>.name` and `.format` key by key and gave each scalar a condition on `<id>.enabled`, so a key that no scalar used was ignored. The keys are now bound to `ScalarsConfiguration` (`@ConfigurationProperties`, `Toggleable`, with the public `PREFIX` and `ENABLED_CONFIG` constants) and `ScalarConfiguration` (`enabled`, `name`, `format`, one for each id). The keys keep their names, and a blank `name`, an invalid `name` and an invalid `format` still fail the startup with a message that names the key.

What changes: a key under `micronaut.graphql.tools.scalars` whose first segment is neither `enabled` nor the id of a standard scalar fails the startup with a `ConfigurationException` that names the key and lists the valid ids. Before, it did nothing.

[source,yaml]
----
# Before: ignored, so local-date stayed enabled
micronaut:
  graphql:
    tools:
      scalars:
        local-dat:
          enabled: false
# Now: fix the id
micronaut:
  graphql:
    tools:
      scalars:
        local-date:
          enabled: false
----

=== BC-49: the observability module is split into graphql-tools-micrometer and graphql-tools-opentelemetry (#570)

`observability` is not the name of a Micronaut module: the official modules are named after their technology, such as `micronaut-micrometer-core` and `micronaut-tracing-opentelemetry-http`, and none ships metrics and tracing in one artifact. The module is now two, each named after its technology:

[cols="3,3", options="header"]
|===
| Before | Now
| `io.micronaut.graphql.tools:micronaut-graphql-tools-observability` | `micronaut-graphql-tools-micrometer` for the metrics, `micronaut-graphql-tools-opentelemetry` for the spans
| `io.micronaut.graphql.tools.observability.GraphQLObservability` | `io.micronaut.graphql.tools.micrometer.GraphQLMetrics`, with the same meter and tag constants
| `:micronaut-graphql-tools-observability:check` | `:micronaut-graphql-tools-micrometer:check` and `:micronaut-graphql-tools-opentelemetry:check`
|===

The configuration keys of BC-39 stay as they are: `micronaut.metrics.binders.graphql.*` belongs to the Micrometer module and `micronaut.graphql.tools.tracing.*` to the OpenTelemetry module. The library still adds exactly one `Instrumentation` bean for both, which now lives in `graphql-tools`, so a request with both modules on costs no more per field than before. The artifact was never published, so there is no relocation POM.

[source,groovy]
----
// Before
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-observability:1.0.0-M4")
// Now: the module of each technology you use
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-micrometer:$graphqlToolsVersion")
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-opentelemetry:$graphqlToolsVersion")
----

=== BC-41: binding failures are a ConfigurationException (#498)

Every failure of the binding happens while the application wires itself at startup, which is what Micronaut calls a configuration failure. `SchemaBindingException` is now a `io.micronaut.context.exceptions.ConfigurationException`, so Micronaut's startup error reporting and the unwrapping of `BeanInstantiationException` treat it like the exceptions of Micronaut itself. The scalars module already threw `ConfigurationException`, so the whole library uses one hierarchy. `SchemaBindingException` stays the one public exception class; the concrete classes stay internal and are caught through the base type. The error codes and messages do not change.

The accessor that returns the failure code follows the bean naming convention:

[source,java]
----
// Before
if (failure.code() == BindingCode.FIELD_NOT_BOUND) { ... }
// Now
if (failure.getCode() == BindingCode.FIELD_NOT_BOUND) { ... }
----

In Groovy and Kotlin, `failure.code` reads the property. A `catch (ConfigurationException e)` or a `catch (RuntimeException e)` that already caught the failure keeps working; a handler that caught `ConfigurationException` for another reason now also sees binding failures, so match on `SchemaBindingException` first when the two need different handling.

See the error reference.

=== BC-47: `ResolverBeanCondition` is internal, `@GraphQLType.value()` is `Class<?>` (#501)

`io.micronaut.graphql.tools.annotation.ResolverBeanCondition` is now `io.micronaut.graphql.tools.internal.resolver.ResolverBeanCondition`, marked `@Internal` and no longer `@Introspected`. `@GraphQLType.value()` is declared `Class<?>`, not the raw `Class`. `GraphQLToolsConfiguration.SchemaConfiguration.DEFAULT_SCHEMA_LOCATION` and `BindingManifest.FORMAT` are constants of the public types and no longer refer to an `internal` package.

Nothing needs to change, unless your code names the condition class in a `@Requires(condition = ...)`: stop doing that, it is not API. A Kotlin or Groovy source that reads `@GraphQLType.value` compiles as before.
