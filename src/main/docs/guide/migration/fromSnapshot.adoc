This page is for applications built on `1.0.0-SNAPSHOT`. No release was published before `1.0.0-M1`, so no published API breaks here. The changes matter for snapshot builds and for anyone who moves to the milestone releases.

The numbers `BC-01` to `BC-19` are the ones of the 1.0.0-M1 release notes, `BC-20` is the one of the 1.0.0-M2 release notes, `BC-21` is the first of 1.0.0-M3, and `BC-22` to `BC-29` follow it. Other later breaking changes are named by their issue number until they get a number. Each change is either on `master` now or marked _pending_ with the issue that will make it.

Changes BC-01, BC-02, BC-04, BC-05, BC-06, BC-10, BC-11, BC-13, BC-15 and BC-17 have no opt-out. There is no legacy mode and no warning period for them. Each startup failure names its fix in the message.

Snippets are Java. The same changes apply to Kotlin and Groovy classes.

== Entries for 1.0.0-M1

=== BC-01: `List<CompletionStage<T>>` is a startup error

Before, a field whose return type was a list of futures was accepted, and the client received the future's `toString()`. Now the startup fails with `UnsupportedReturnTypeException`. The message names the fix: return `CompletionStage<List<T>>`, for example by combining the element futures with `CompletableFuture.allOf`, or load the elements with a DataLoader.

Status: approved, no opt-out.

[source,java]
----
// Before: accepted, and the client received the future's toString()
public List<CompletionStage<Author>> authors(Book book) { ... }

// After: one future for the whole list
public CompletionStage<List<Author>> authors(Book book) { ... }
----

=== BC-02: wrappers and `Optional` placement

Before this change, only `CompletionStage` was unwrapped. Most of the shapes below therefore already failed at startup, with a different message. The change is the message, and three shapes that now work:

* `Optional<T>` on a nullable field or on each element of a nullable list (an empty `Optional` becomes `null`);
* `DataFetcherResult<T>` on a field or on each list element;
* `Publisher<T>` on a field of the subscription type.

These shapes fail at startup with `UnsupportedReturnTypeException`:

* `Optional<T>` on a non-null GraphQL type, such as `String!` or `[String!]`;
* wrappers in the wrong order or repeated;
* `Publisher` on a field that is not a subscription field, or inside a list. `Publisher` on other fields stays an error until #75 (pending). Until then, return a `CompletionStage`, for example `Mono#toFuture()`;
* a subscription field that does not return a `Publisher`, optionally inside a `CompletionStage`.

Status: approved, no opt-out.

[source,java]
----
// Schema: nickname: String!
// Before and after: fails at startup, Optional is not allowed for a non-null type
public Optional<String> nickname(User user) { ... }

// Fix: make the GraphQL field nullable (nickname: String), or return the value itself
public String nickname(User user) { ... }

// Publisher on a query field fails at startup
public Flux<String> greeting() { ... }

// Fix: return a CompletionStage
public CompletionStage<String> greeting() {
    return Mono.just("hello").toFuture();
}
----

=== BC-03: build, POM and publishing

Before, the build required Java 21, and the published POM declared extended-scalars 21.0 (it was 20.2 before).

Now the library compiles to Java 17 bytecode (`--release 17`). The project's CI builds it on JDK 21 and 25. Nothing is published to Maven Central or to a snapshot repository.

Status: not covered by #79; the release notes list it.

Fix: run the library on Java 17 or newer. Build the full project, including `graphql-tools-processor`, on JDK 21 or newer; on JDK 17 only the library module can be checked. To use the library, build and publish it to a local or private repository. If you pin `graphql-java-extended-scalars`, pin the version your build resolves: check it with `./gradlew dependencies`.

=== BC-04: `@Inherited` resolver stereotypes

`@GraphQLRootResolver` and `@GraphQLTypeResolver` are `@Inherited`. A bean that extends an annotated class is a resolver too. The subclass cannot remove an inherited annotation, so a fake or a subclass that is also a bean can bind the same field as the original and create an ambiguity.

Fix: annotate the fake or the subclass with `@Replaces(<original>.class)`. A `@Requires(env = "test")` alone does not help: both beans are active in the test environment. To add behaviour around a resolver, use a Micronaut AOP interceptor, not a subclass bean.

Status: approved, no opt-out. Pending #73 (M4): the stereotype is removed from contracts. A `@Singleton` subclass of an implementation stays a second resolver, so `@Replaces` stays the fix.

[source,java]
----
@GraphQLTypeResolver(Book.class)
@Singleton
public class BookLabelResolver {
    public String label(Book book) { ... }
}

// Fake for the tests: replaces the original bean instead of competing with it
@Replaces(BookLabelResolver.class)
@Singleton
public class FakeBookLabelResolver extends BookLabelResolver {
    @Override
    public String label(Book book) { return "test label"; }
}
----

=== BC-05: getters that only the implementation declares

An object type mapped to a Java interface that has its own introspection reads its properties through that introspection. A getter that only an implementation class declares does not bind any more. Before, it bound silently. Now the startup fails with `MethodNotFoundException`, which names the interface, the implementation that declares the getter, and the fix.

Fix: declare the getter on the interface. Removing the interface's own introspection (the `@GraphQLType` or `@Introspected` annotation on the interface) is not a complete fix in strict mode, so declare the getter.

Status: approved, no opt-out.

[source,java]
----
@Introspected
public interface Book {
    String getTitle();

    // Before: declared only in BookImpl, it bound silently. Now: declare it here.
    String getSummary();
}
----

=== BC-06: member mapped outside the declared Java type

A union member or an interface implementation that is mapped to a Java type which cannot be the field's declared Java interface fails the startup with `IncorrectMemberMappingException`. The check is narrowed: only provably disjoint pairs fail, that is a `final` class that does not implement the interface, or classes that are unrelated. Other mappings are accepted.

Fix: map the member to a class that matches the field's declared Java interface.

[source,java]
----
public interface Coded {
    String getCode();
}

// Before: Stray is final and does not implement Coded, so no object can be both.
// Startup fails with IncorrectMemberMappingException.
public final class Stray {
    public String getCode() { return "stray"; }
}

// After: Stray implements the Java interface that the field declares
public class Stray implements Coded {
    @Override
    public String getCode() { return "stray"; }
}
----

Status: approved, no opt-out; narrowed to provably disjoint mappings.

=== BC-07: `UnionTypeResolver` renamed to `AbstractTypeResolver`

The public class `UnionTypeResolver` is renamed to `AbstractTypeResolver`, in package `io.micronaut.graphql.tools.schema`. Dictionary error messages changed too.

Fix: rename the type in imports and in every reference.

[source,java]
----
// Before
import io.micronaut.graphql.tools.schema.UnionTypeResolver;

// After
import io.micronaut.graphql.tools.schema.AbstractTypeResolver;
----

=== BC-08: input class properties

Two checks are startup errors now:

* A property of an input class that the GraphQL input type does not define. It can be set by a setter or the constructor, but no request can set it. Strict mode fails the startup for these, in one `UnmappedInputPropertiesException`.
* An input field that the input class cannot set. This fails with `InputFieldNotSettableException` and has no opt-out.

Opt-out for the first check: `micronaut.graphql.tools.checks.unmapped-input-property` set to `warn` or `ignore` accepts these properties. Setting `strict: false` also accepts them, with a warning. The second check has no opt-out.

Fix: add the field to the input type, or remove the property. Make the field settable with a setter or the constructor.

Status: the unmapped-property check has an opt-out, the unsettable field has none.

[source,java]
----
// Schema: input CreateBook { title: String! }
// Fails at startup in strict mode: the input type does not define isbn
@GraphQLInput
public class CreateBook {
    private String title;
    private String isbn;

    // getters and setters for title and isbn
}

// Fix: add `isbn: String` to the input type, or remove the property
----

=== BC-09: primitive for a nullable built-in scalar

In strict mode, an argument or an input class property declared as a primitive (`int`, `boolean`, `double`, ...) for a nullable built-in scalar (`Int`, `Boolean`, `Float`, `Long`, ...) fails the startup with `IncorrectClassMappingException`. A `null` cannot reach a primitive, so the value would be the primitive's default.

Fix: use the wrapper class, or make the GraphQL type non-null.

Opt-out: `micronaut.graphql.tools.checks.nullable-primitive` set to `warn` or `ignore` (`strict: false` is `warn` for every check).

[source,java]
----
// Schema: quantity: Int (nullable). Fails in strict mode.
public Book reserve(int quantity) { ... }

// Fix: the wrapper class
public Book reserve(Integer quantity) { ... }
----

=== BC-10: the `GraphQL` bean is created only when there is none

The library creates its `GraphQL` bean only when the application does not define one. The `GraphQLSchema` bean is exposed, so the application can use it. The schema is still bound at startup, so a broken binding fails the startup even when the application defines its own `GraphQL` bean.

Which application bean makes the library step aside: the library's `GraphQL` and `GraphQLSchema` beans step aside only for an application bean of the same type that has no qualifier, or that is `@Primary`. A bean with a qualifier, such as `@Named("admin")`, is a secondary bean that is injected by its qualifier. It does not replace the library's bean, and the library's beans are `@Primary`, so an unqualified injection point still gets them. A bean registered at runtime counts like any other. A bean that an enabled `@Replaces` bean replaces does not count (the `bean`, `factory` and `named` members are matched; the `qualifier` member is not evaluated, so a bean replaced that way still counts), and an `@EachProperty` or `@EachBean` template counts by the beans it expands to: named expansions do not replace the library's bean, an expansion that is unqualified or primary does. When the application provides its own `GraphQLSchema` bean, the library binds nothing, and the `BindingManifest` bean fails with a message that names that bean. At startup the library logs at INFO which `GraphQL` and `GraphQLSchema` beans are in use and why the library's bean was or was not created (logger `io.micronaut.graphql.tools.BeanSelectionLogger`).

Fix: to change the library's `GraphQL` without replacing it, add a `GraphQLBuilderCustomizer`. To replace it, define your own `GraphQL` bean.

Status: approved, no opt-out.

[source,java]
----
@Singleton
public class GraphQLTuning implements GraphQLBuilderCustomizer {
    @Override
    public void customize(GraphQL.Builder builder) {
        // change the builder the library uses
    }
}
----

=== BC-11: a bare `SchemaDirectiveWiring` bean

A `SchemaDirectiveWiring` bean that no `SchemaDirective` bean wraps was ignored before. It is a startup error now, `UnwrappedDirectiveWiringException`. The message names the two wrappers.

Fix: wrap the wiring. Use `SchemaDirective.named(name, wiring)` for one directive. Use `SchemaDirective.everyElement(names, wiring)` only for a wiring that must see every schema element: graphql-java calls it for each element, so it must check the directives itself.

Status: approved, no opt-out.

[source,java]
----
// Before: a bare bean, ignored
@Singleton
public class AuthWiring implements SchemaDirectiveWiring { ... }

// After: wrapped in a SchemaDirective bean, produced by a factory
@Factory
public class AuthDirectives {
    @Singleton
    SchemaDirective authDirective(AuthWiring wiring) {
        return SchemaDirective.named("auth", wiring);
    }
}
----

=== BC-12: directives without a wiring

A directive that the schema applies without a wiring is a startup error, `UnwiredDirectivesException`, which lists where each one is applied. A wiring is a `SchemaDirective` bean, a `RuntimeWiringCustomizer` that registers a wiring under the directive's name, or a name in `resolver-directives`. graphql-java's built-in directives need none.

Fix: add a wiring. If the directive has no effect at runtime, list it in `micronaut.graphql.tools.allow.inert-directives`.

Opt-out: `allow.inert-directives` lists the names. With `checks.unwired-directive: warn` (or `strict: false`) the startup logs one warning that lists them, and the schema keeps the directives without effect. `ignore` skips the check.

Status: opt-out exists.

[source,yaml]
----
micronaut:
  graphql:
    tools:
      allow:
        inert-directives:
          - deprecated-since
----

=== BC-13: a `RuntimeWiringCustomizer` that replaces the library's wiring

A `RuntimeWiringCustomizer` may only add to the runtime wiring. One that replaces the library's wiring fails with `RuntimeWiringOverrideException`. On graphql-java 25 the builder rejects the first replaced default data fetcher, type resolver or scalar itself, with `StrictModeWiringException`, so the startup fails with that exception instead. A replaced data fetcher of a library-wired field is always reported as `RuntimeWiringOverrideException`.

Fix: add to the library's wiring in the customizer. To serve a field with a hand-written `DataFetcher`, return its coordinate from `claimedFields()`. The library then does not bind the field. The library does not traverse the return type of a claimed field, so that type must also be reached through another bound field, or listed in `allow.unreachable`.

Status: approved, no opt-out. `claimedFields()` is on `master`.

[source,java]
----
@Singleton
public class BookFetcherCustomizer implements RuntimeWiringCustomizer {
    @Override
    public void customize(RuntimeWiring.Builder builder) {
        builder.type("Query", type -> type.dataFetcher("latestBook", env -> latestBook()));
    }

    @Override
    public Set<FieldCoordinates> claimedFields() {
        return Set.of(FieldCoordinates.coordinates("Query", "latestBook"));
    }
}
----

=== BC-14: a property and a type resolver bind one field

When a member of the Java type (a property or a `@GraphQLField` method) and a type resolver method can both bind a field, the startup fails with `AmbiguousBindingException`, which names the field and both members. Before, the property won silently.

[source,java]
----
// Schema: type Book { id: ID! }. The getter and the type resolver method both bind Book.id,
// so startup fails with AmbiguousBindingException.
public class Book {
    public String getId() { return "1"; }
}

@GraphQLTypeResolver(Book.class)
@Singleton
public class BookResolver {
    public String id(Book book) { return book.getId(); }
}

// After: the getter is ignored, so the type resolver method alone binds the field
public class Book {
    @GraphQLIgnore
    public String getId() { return "1"; }
}
----

Fix: remove one of the two members. Or choose the winner: set `micronaut.graphql.tools.precedence` to `property-first` (the old behaviour) or `resolver-first`, or mark the field with a schema directive that is listed in `resolver-directives`, so that the type resolver method binds it. A getter can also carry `@GraphQLIgnore`, so the type resolver binds the field without an ambiguity.

Opt-out: `micronaut.graphql.tools.precedence: property-first`. `strict: false` does not change this outcome.

The default value of `precedence` is named `fail` (BC-29). Pending #236 (M3): the ambiguity becomes a `SchemaBindingException` with an error code. The behaviour of the options above is unchanged.

[source,yaml]
----
micronaut:
  graphql:
    tools:
      precedence: resolver-first
----

=== BC-15: root resolvers per operation type

Root resolver methods are scoped to one root operation type (`Query`, `Mutation` or `Subscription`). Before, the first bean found won when two root methods bound one field. Now two root methods for one field are a startup error, `MultipleMethodsFoundException`. A method without a coordinate binds the field of its name on every root operation type. Strict mode also fails on a method without a coordinate that binds the same field name on several operation types.

Fix: when the methods serve different operation types, give each one its own coordinate, for example `Query.ping` and `Mutation.ping`. Two methods with the same coordinate still conflict, so remove one of them. When one bean is meant to override another, annotate the overriding bean with `@Replaces`.

Status: approved, no opt-out.

[source,java]
----
@GraphQLRootResolver
public class PingQuery {
    @GraphQLSchemaCoordinate("Query.ping")
    public String ping() { return "pong"; }
}

@GraphQLRootResolver
public class PingMutation {
    @GraphQLSchemaCoordinate("Mutation.ping")
    public String ping() { return "pong"; }
}

// A test fake that overrides PingQuery: @Replaces drops the original bean, so only the fake binds Query.ping
@Replaces(PingQuery.class)
@GraphQLRootResolver
public class FakePingQuery extends PingQuery {
    @Override
    @GraphQLSchemaCoordinate("Query.ping")
    public String ping() { return "test pong"; }
}
----

=== BC-16: strict mode is on by default

`micronaut.graphql.tools.strict` defaults to `true`. Strict mode fails the startup on bindings that work but are probably mistakes: stale resolver methods, Java enum constants without a schema value, dictionary entries for types that are not bound, interface-mapped types without their own introspection, unused enum, input and scalar types, and the other findings that the strict mode checks in the README list. Most findings are also a `!` line of the binding manifest. Some have no manifest line, for example interface-mapped types without their own introspection, and primitives for nullable built-in scalars; the startup exception is their only report.

Fix: fix each finding. A member that binds no field on purpose can carry `@GraphQLIgnore`. Or set `strict: false`.

Opt-out: `micronaut.graphql.tools.strict: false` makes every check `warn`, including unreachable object, interface and union types (BC-27). A single check is relaxed with `checks.<code>`, a single finding with `allow.findings`.

=== BC-17: `extend type` fields are bound and checked

Fields of an `extend type` definition are bound and checked like any other field. Before, graphql-java's default data fetcher served them without any check. The startup now names the coordinate of an extension field that nothing binds.

Fix: give the field a resolver or a property. If a `RuntimeWiringCustomizer` serves it, return its coordinate from `claimedFields()`. A type that such a field returns must still be reached through another bound field, or listed in `allow-unreachable`.

Status: approved, no opt-out.

[source,java]
----
// Schema: extend type Query { latestBook: Book }
// Before: served by graphql-java's default data fetcher, without a check.
// Now: give it a root resolver method like any other field
@GraphQLRootResolver
public class LatestBookQuery {
    @GraphQLSchemaCoordinate("Query.latestBook")
    public Book latestBook() { ... }
}
----

=== BC-18: unreachable types

An object, interface or union type that no field reachable from a root operation type returns fails the startup. The error lists all of them at once. Enum, input and scalar types are checked in strict mode.

An `allow.unreachable` entry that is no longer unreachable fails the startup, so the list cannot go stale. An allowed or ignored type also covers the enum, input and scalar types that it uses.

Fix: bind the type through a field, remove it from the schema, or list it in `allow.unreachable`. Remove stale entries from `allow.unreachable`.

Opt-out: `micronaut.graphql.tools.checks.unreachable-type` set to `warn` or `ignore`. The types stay in the schema with graphql-java's default data fetchers; `warn` logs them.

[source,yaml]
----
micronaut:
  graphql:
    tools:
      allow:
        unreachable:
          - Legacy
----

=== BC-19: resolver parameters bind by name

Resolver parameters are bound to field arguments by name, not by position. A parameter without an argument of its name, or two parameters bound to one argument, fails the startup with `IncorrectArgumentNameException`.

Fix: rename the parameter to the argument name, or add `@GraphQLArgument("<argument name>")`.

Status: breaking by design; no opt-out. The runtime half is on `master` (PR #257). The compile-time visitor of `graphql-tools-processor` applies the same rule (#15), with the same code and coordinate. The JSR-269 processor that a build registers until #291 still compares parameters by position, so a build does not yet catch a misnamed parameter.

A parameter of a method inherited from a class file that carries no parameter names (built without `-parameters`, or without `-g` for a method with a body) has the name `arg0`. The failure then says to compile the class that declares the method with `-parameters`, or to add `@GraphQLArgument`. The guide page "Inputs" lists where the names come from.

[source,java]
----
// Schema: book(id: ID!): Book
// Before: bound by position. Now: fails, there is no argument named isbn.
public Book book(String isbn) { ... }

// Fix: rename the parameter
public Book book(String id) { ... }

// Or keep the name and bind the argument explicitly
public Book book(@GraphQLArgument("id") String isbn) { ... }
----

=== BC-20: the `graphql-tools` mapper seam is internal (#173)

The `@Named("graphql-tools")` `ObjectMapper` bean name and the `INPUT_OBJECT_MAPPER` constant are internal (`@Internal`) and no longer documented. The README no longer describes Jackson-defined input behaviour (`@JsonIgnore`, naming strategies, a named mapper). Applications should not depend on the bean. BC-23 (#37) removes the mapper: the input conversion no longer reads an `ObjectMapper`.

Fix: remove the `graphql-tools` bean and any reference to `INPUT_OBJECT_MAPPER`. Customize the input conversion with `TypeConverter` beans (BC-23).

== Entries for 1.0.0-M3

=== BC-21: enums need a bean introspection (#33)

The library wires one values provider per bound enum, built at startup from the enum's bean introspection (`EnumBeanIntrospection`, generated at compile time). graphql-java then coerces an enum argument, an enum input field and an enum default value to the Java constant itself, so the resolver receives it without a conversion call. The library no longer reads enum constants by reflection (`Class#getEnumConstants()`). An enum without a bean introspection fails the startup with `ClassNotIntrospectedException`, which names the class and the annotation to add.

Fix: annotate each Java enum that a field, argument or input field uses with `@Introspected`. Micronaut Serialization's `@Serdeable` also introspects the enum. The compile-time processor does not check this yet.

A `RuntimeWiringCustomizer` that registers its own `enumValues` provider for a bound enum now fails the startup with `RuntimeWiringOverrideException`, like any other replacement of the library's wiring.

[source,java]
----
// Before: accepted, the resolver received the constant through a conversion of the enum name
public enum Color { RED, GREEN }

// After: bean introspection generated at compile time
@Introspected
public enum Color { RED, GREEN }
----

=== BC-22: one code system for checks and errors (#237)

Every strict check, every startup failure and every compile-time diagnostic has one code, from the `BindingCode` enum of `graphql-tools-binding`. The code is the same token in four places: the `[code]` at the start of the message, `SchemaBindingException#code()`, the word after `!` in a binding manifest line, and the check name that `checks.<code>` and `allow.findings` use. The list is in the error reference.

What breaks for code that read the old forms:

* Every startup exception extends the new public `SchemaBindingException`, and its message starts with `[code] `. A test that compares a whole message, or that checks `startsWith`, needs the prefix. A test that checks `contains` is not affected.
* The manifest `!` lines changed their first word, as the summary table lists. Code that reads `!unbound`, `!unusedDictionary`, `!ambiguous`, `!unreachable` or `!unwiredDirective` lines reads the codes now. The compile-time manifest that the JSR-269 processor writes keeps the old words until #144 removes the processor.
* `BindingFailuresException` and `StrictModeException` tag each finding with its own code. `StrictModeException#getCodes()` returns the check code of each problem.

Fix: match on `exception.code()` (or on the `[code]` token), and read the manifest kinds from the table in the error reference.

[source,java]
----
try {
    applicationContext.getBean(GraphQL.class);
} catch (BeanInstantiationException e) {
    if (e.getCause() instanceof SchemaBindingException failure
            && failure.code() == BindingCode.UNBOUND_ENUM_CONSTANT) {
        // ...
    }
}
----

=== BC-23: arguments and input objects are converted from `BeanIntrospection` (#37)

Before, every list, input object and enum argument went through Jackson's `convertValue` on each request. Now the library builds one converter per argument and per input type at startup, from the declared type and from the bean introspection that Micronaut generated at compile time, and a request runs no Jackson and no reflection. Instances are built through the introspected constructor, then the remaining input fields are set through their `BeanProperty`; a field the client leaves out is not set, and an `ArgumentValue` is set to `omitted()` from the keys of the coerced map, in the same pass.

What stops being the input contract:

* Jackson annotations on an input class (`@JsonIgnore`, `@JsonProperty`, `@JsonCreator`, `@JsonDeserialize`) and the naming strategy of an `ObjectMapper`. An input field is bound to the property or constructor parameter of the same name.
* `FAIL_ON_UNKNOWN_PROPERTIES` and every other `ObjectMapper` setting. An `ObjectMapper` bean, whatever its name, is not read. The `INPUT_OBJECT_MAPPER` constant is removed.
* A list argument or input field is converted into `List`, `Collection`, `Iterable` (an `ArrayList`), `Set` (a `LinkedHashSet`), `SortedSet` (a `TreeSet`), `Deque` or `Queue` (a `LinkedList`). Any other declared collection fails the startup with `UnsupportedInputTypeException`.
* `InputFieldNotSettableException` now says that the property has no setter and no constructor parameter. A property with an `ArgumentValue` type may be write-only, and an `ArgumentValue` property that an input type does not define is set to `omitted()`.

Fix: name the properties and the constructor parameters of an input class like the input fields. Put a `TypeConverter<Map, SomeInput>` bean in the application for an input class that needs a conversion of its own (the bean builds the whole instance, `ArgumentValue` properties included), and a `GraphQLScalarMapping` for a custom scalar. A scalar value that is not an instance of the declared class goes through the Micronaut `ConversionService`, which holds the application's `TypeConverter` beans.

[source,java]
----
// Before: Jackson read the annotation, and the field "legacy_code" bound to "legacyCode"
@GraphQLInput
public class ItemInput {
    @JsonProperty("legacy_code")
    private String legacyCode;
}

// After: the property carries the name of the input field
@GraphQLInput
public class ItemInput {
    private String legacyCode;
    // getter and setter, or a constructor parameter named legacyCode
}
----

=== BC-25: the binding manifest has a specified format, version 2 (#90)

The manifest format is specified on the "Binding Manifest" page and its version is the number on the first line. Version 2 differs from version 1 in four ways:

* The separators are ASCII: ` -> ` replaces the arrow and ` ; ` replaces the middle dot, in entries and in findings. The text is ASCII only: a character outside `0x20` to `0x7e` and the backslash in a part are written `\uXXXX`. A part that holds a line break is escaped instead of failing the rendering.
* A `scalar` line names the scalar in the member part (`Long -> scalar ; Long ; - ; -`). It named the `Coercing` class (`graphql.scalars.java.JavaPrimitives$1`), which could be an anonymous class and changed with the graphql-java version. A `claimed` line names the customizer by a class a reader can find, never an anonymous or generated class.
* The schema hash is computed over the definitions sorted by name, with the extensions of a name sorted by their printed text. The same schema files loaded in any order give one hash. The hash of every schema differs from the hash of version 1.
* The first line is `# graphql-binding-manifest 2`.

Fix: regenerate every checked-in manifest, and change a reader that splits lines on the arrow or the middle dot to split on ` -> ` and ` ; `. A reader should check the version on the first line and refuse a version it does not know. The compile-time manifest of the JSR-269 processor and the manifest of the startup are both written in version 2.

=== BC-26: Jackson leaves the `api` scope (#36)

The library's `api` scope brought `micronaut-jackson-databind` to every application. The library itself does not use Jackson (#37, BC-23), so the dependency leaves the `api` scope and the library no longer declares Jackson at compile or runtime. An application that gets its JSON from Jackson declares `micronaut-jackson-databind` itself. An application that uses Micronaut Serialization declares `micronaut-serde-jackson` (or another Serde JSON module). Without any JSON codec, an application that serves HTTP fails at startup with `No bean of type [io.micronaut.json.JsonConfiguration] exists`.

Fix: add the JSON dependency your application uses to its build, for example:

[source,groovy]
----
dependencies {
    implementation("io.micronaut:micronaut-jackson-databind") // or io.micronaut.serde:micronaut-serde-jackson
}
----

=== BC-27: per-check severity and removed keys (#86)

Each of the ten checks has a severity, set with `micronaut.graphql.tools.checks.<code>`: `fail` (the default of every check), `warn` (log the finding and go on) or `ignore` (skip the check; it does no work). `strict` is the shorthand for the checks without an entry: `true` leaves them at `fail`, `false` makes them `warn`. `unreachable-type` is split into two codes: `unreachable-type` for object, interface and union types, and `unreachable-value-type` for enum, input and scalar types. `strict: false` now also warns on unreachable object, interface and union types, which failed before. `precedence` does not depend on `strict`.

What breaks:

* Six keys are removed, with no alias (`input.detect-omission` of BC-28 fails the same way). If one is set, the startup fails with `[removed-configuration-key]` and names the replacement:

[cols="2,3", options="header"]
|===
| Removed key | Replacement
| `micronaut.graphql.tools.unreachable-types` | `micronaut.graphql.tools.checks.unreachable-type` and `micronaut.graphql.tools.checks.unreachable-value-type` (the old `ignore` is `warn`)
| `micronaut.graphql.tools.input.unmapped-properties` | `micronaut.graphql.tools.checks.unmapped-input-property`
| `micronaut.graphql.tools.allow-unreachable` | `micronaut.graphql.tools.allow.unreachable`
| `micronaut.graphql.tools.inert-directives` | `micronaut.graphql.tools.allow.inert-directives`
| `micronaut.graphql.tools.schema-customizer-directives` | `micronaut.graphql.tools.allow.schema-customizer-directives`
| `micronaut.graphql.tools.unwired-directives` | `micronaut.graphql.tools.checks.unwired-directive`
|===

* An unknown check code or a severity other than `fail`, `warn` or `ignore` fails the startup with `[invalid-check-setting]`.
* A check at `ignore` writes no `!` line to the binding manifest. The checks `root-method-several-operations`, `interface-read-through-implementation` and `nullable-primitive` now write `!` lines too.
* A primitive for a nullable built-in scalar fails with the code `nullable-primitive` (was `incorrect-class-mapping`).
* Three new codes: `invalid-check-setting`, `removed-configuration-key` and `invalid-allow-findings`.

New: `allow.findings` takes lines of the binding manifest, exactly as the manifest writes them (`!unbound-resolver-method example.Query#helper(java.lang.String)`), and accepts exactly that finding. An entry that is not the line of a check, whose check is `ignore`, or that matches no finding fails the startup. `allow.unreachable`, `allow.inert-directives` and `allow.schema-customizer-directives` are validated as before.

Fix: rename the keys as in the table. The JSR-269 processor options keep their names until #291.

[source,yaml]
----
micronaut:
  graphql:
    tools:
      checks:
        unreachable-value-type: warn
        unwired-directive: ignore
      allow:
        unreachable:
          - Legacy
        findings:
          - "!unbound-resolver-method example.Query#helper(java.lang.String)"
----

=== BC-28: `ArgumentValue` needs no option (#159)

`micronaut.graphql.tools.input.detect-omission` (default `false`) was a second opt-in next to the declared `ArgumentValue` type: with the option off, an `ArgumentValue` parameter or property failed the startup. The option is removed. The converter of an input type handles omission when the type has an `ArgumentValue` property or constructor parameter, and a type without one pays nothing.

* A configuration key `micronaut.graphql.tools.input.detect-omission` fails the startup with `[removed-configuration-key]`, which says to declare `ArgumentValue` on the resolver parameter or the input property.
* The compile-time option `-Amicronaut.graphql.tools.input.detectOmission` fails the compilation as an unknown option under the `micronaut.graphql.tools.` prefix.

Fix: delete the key or the option. Nothing else changes for an application that set it to `true`.

=== BC-29: one precedence rule for object and interface fields (#105)

A field can be bound by a member of its Java type (a property or a `@GraphQLField` method) and by a type resolver method (of the type, or of an interface that declares the field). One rule decides it, for object and interface fields alike, at startup and in the compile-time checks that apply it:

. A member marked `@GraphQLIgnore` is no member, so the type resolver method binds the field.
. A field that carries a directive listed in `resolver-directives`, or whose type resolver method declares its coordinate with `@GraphQLSchemaCoordinate`, is bound by the type resolver method. Nothing is logged.
. Any other ambiguity follows `micronaut.graphql.tools.precedence`: `fail` (the default) fails the startup with `[precedence-ambiguity]`, `resolver-first` binds the resolver method and `property-first` binds the member; both log the ambiguity at WARN and write a `!precedence-ambiguity` line to the manifest.

`precedence` does not depend on `strict`, and it is not a `checks.<code>` entry. `property-first` stays through 1.0.

What breaks:

* The value `strict` is renamed `fail`, and `strict` is rejected: the startup fails with `[removed-configuration-key]` that names `fail`. The default does not change.
* A type resolver method that declares its coordinate now wins over a member of the same field. Before, with the default it was an ambiguity, and with `property-first` the startup failed with `[unknown-schema-coordinate]` because the property bound the field.

The Relay `Node.id` case is written with the coordinate on the interface resolver, so an entity keeps its own `getId()`:

[source,java]
----
@GraphQLTypeResolver(Node.class)
public class NodeResolver {
    @GraphQLSchemaCoordinate("Node.id")
    public String id(Node node) { return globalId(node); }
}
----

Fix: write `precedence: fail` or delete the line. The error message names the options for one field (a resolver directive, `@GraphQLSchemaCoordinate`, `@GraphQLIgnore`) and for every field (`precedence: resolver-first` or `property-first`).

== Pending changes

The following changes are planned and are not on `master` yet. Their behaviour is not described as current. Each entry names the issue that makes the change.


=== BC-24: schema files are `*.graphqls` (#17)

The runtime finds the schema files itself (`micronaut.graphql.tools.schema.locations`, default `classpath:graphql/**/*.graphqls`), and the compile-time processor reads the same files with the same code. Both read `*.graphqls` only, so a client operation file (`*.graphql`) in the schema directory is not a schema file and cannot break the build. Before, the processor read every `*.graphql` file as schema.

Rename the schema files that end in `.graphql` to `.graphqls`. A `TypeDefinitionRegistry` bean of your own still replaces the discovery, and a schema without a `schema { }` block and with a `Query` type now binds with `Query`, `Mutation` and `Subscription` as roots.

=== #109: the public exceptions

Startup failures collapse into one public `SchemaBindingException` with a stable error code. The subclasses become internal, and the error codes are listed in the guide. Match on the code, not on the exception subclass. Internal types move out of the API packages.

=== #236: the ambiguity exception

`AmbiguousBindingException` becomes internal with #109. Match on the code `precedence-ambiguity`, which is on `master` since BC-22; the message keeps naming the field coordinate and both members.

=== #144 and #291: the compile-time processor

The visitor replaces the JSR-269 processor of `graphql-tools-processor`. #291 registers the visitor, removes the JSR-269 service files, and renames the options:

* `micronaut.graphql.tools.sdlDir` is replaced by `micronaut.graphql.tools.processor.schema.dirs`;
* `micronaut.graphql.tools.processor.checks` (`true` by default) switches the compile-time checks off when it is `false`;
* `micronaut.graphql.tools.processor.module.dir` (optional) is the project directory of the module that sets `schema.dirs`; it makes a `schema.dirs` left behind by an earlier module of the same JVM fail the build instead of being used.

Until #291 lands, the JSR-269 processor reads the options it has today, `sdlDir` among them. #144 then deletes the JSR-269 code. Builds that pass the old options fail once their names are removed.

== Migration recipe

To move an application from `1.0.0-SNAPSHOT` in one pass, set these options first. They relax the optional checks and write the binding manifest. They do not relax the changes without an opt-out (BC-01, 02, 04, 05, 06, 10, 11, 13, 15 and 17): the startup still fails for those, and each failure must be fixed as it is reported:

[source,yaml]
----
micronaut:
  graphql:
    tools:
      strict: false
      precedence: resolver-first
      manifest:
        enabled: true
----

`strict: false` makes every check `warn`, including unreachable object, interface and union types, so none of them fails the startup (BC-27).

`resolver-first` is the migration setting, but it is not the snapshot's behaviour. On object types the property used to win silently, so `resolver-first` can return a different value for a field that a property and a type resolver method both bind. Read the ambiguities in the manifest first, or use `precedence: property-first` to keep the old values while you fix them.

Then read the `!` lines of the binding manifest, and fix, annotate with `@GraphQLIgnore`, or allow each one. `@GraphQLIgnore` is read at runtime; the JSR-269 processor does not read it yet, so a member that carries it can still fail the build. The visitor (#291 makes it the default) applies the same rules.

When the runtime findings are fixed, add `graphql-tools-processor` to the build. It needs its own build option, `-Amicronaut.graphql.tools.sdlDir=<directory of the SDL files>` (see the Compile-Time Verification page). It does not read the runtime settings above, and it needs JDK 21 or newer to build.
