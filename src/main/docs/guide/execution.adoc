This page describes where a GraphQL operation runs and which thread it uses. The library owns the GraphQL invocation, so one setting decides it for HTTP and WebSocket alike.

== What runs where

The transport (`micronaut-graphql`) receives an operation on a Netty event loop thread. Its own invocation would run parsing, validation and every synchronous resolver there: one resolver that blocks, for example on JDBC, gRPC or `join()`, would stall that event loop and so the server.

The library replaces the transport's `GraphQLInvocation`. For each operation it hops once to an executor, before graphql-java runs:

* the operation is received on the event loop;
* one task goes to the executor (`blocking` by default);
* on that executor the library builds the `ExecutionInput`, calls your `GraphQLExecutionInputCustomizer`, and calls graphql-java, which parses and validates the query and runs every synchronous resolver.

There is one thread change per operation. A field hops only when you annotate it with `@ExecuteOn` (see <<executeOn,@ExecuteOn per field>>): the library adds no task, no future and no thread-local read per field, and a trivial field costs the same as before.

The `PropagatedContext` of the receiving thread (the request, and what your filters add, such as security and tracing elements) is captured once and installed in the task when the executing thread does not hold it already, so `ServerRequestContext.currentRequest()`, `@RequestScope` beans and the security service work in your resolvers.

== The executor key

[source,yaml]
----
micronaut:
  graphql:
    tools:
      execution:
        executor: blocking
----

`micronaut.graphql.tools.execution.executor` is a Micronaut executor name, or `none`. It is resolved once at startup.

[cols="1,4", options="header"]
|===
| Value | Operations run on
| `blocking` (the default) | Micronaut's blocking executor: virtual threads on JDK 21 and later, the `io` pool on JDK 17. Micronaut chooses; the library makes no call that needs JDK 21.
| `io` | The `io` pool.
| `virtual` | A virtual thread per operation. JDK 21 and later only.
| any other name | An executor you configure under `micronaut.executors.<name>`, or an `ExecutorService` bean with that `@Named` qualifier.
| `none` | The thread that receives the operation: the Netty event loop over HTTP and WebSocket. No hop, no extra thread change.
|===

`scheduled` is rejected: it is the executor for scheduled tasks, not for work. A name that matches no executor bean, and `virtual` on JDK 17, fail the startup with `[unknown-executor]`, which lists the executor beans that exist.

The default is `blocking` because the library cannot prove that a resolver never blocks. `none` is for applications whose resolvers never block and that want to avoid the hop; it is the behaviour of the transport's own invocation. Size a bounded executor for the operations that wait on it: when it rejects the hop, the client gets a GraphQL response with the status 200, `data` of `null` and one error whose `extensions.code` is `EXECUTION_REJECTED`, and the library logs a warning.

[source,yaml]
----
micronaut:
  executors:
    graphql:
      type: fixed
      nThreads: 32
  graphql:
    tools:
      execution:
        executor: graphql
----

The cost of the hop is measured by the `InvocationBenchmark` of the `benchmarks` module (see CONTRIBUTING.md): it reports the time and the allocation of an operation on the calling thread, with one hop to a virtual-thread executor and to a platform pool, and of the library's own invocation.

[[executorNone]]
=== Executor none

With `executor: none` there is no hop: the operation runs on the thread that receives it. If the application's `GraphQLExecutionInputCustomizer` answers on another thread, the operation continues on the thread that completes its publisher. graphql-java parses and validates there, and every synchronous resolver runs there. The library does not move the operation back, and the propagated context of the receiving thread is not restored on that thread. An event-loop thread of another system, or a pool the application did not intend, then runs the rest of the operation.

== Order of the steps

After the hop the library runs, in this order:

. build the `ExecutionInput` from the query, the operation name and the variables, put the library's per-execution state in its `GraphQLContext`, and set the lazy `DataLoaderRegistry` (only when the application has loader beans);
. call the application's `GraphQLExecutionInputCustomizer` (skipped when it is the transport's default one);
. put the state back in the `GraphQLContext` when the customizer returned a fresh `ExecutionInput`;
. call every `GraphQLContextContributor`, in order;
. run graphql-java.

The customizer therefore runs on the executor and may block. A customizer that publishes its input on another thread makes the operation hop to the executor once more (with `executor: none` it does not, see <<executorNone,Executor none>>). The state is one object per execution (one per WebSocket operation): it holds the captured context, the transport, the request, the response and the connection attributes.

The state is also the read-only `GraphQLExecutionRequest` that the context contributors receive. The registry is the library's own: an application with a `DataLoaderRegistry` bean fails the startup (BC-36). See the Data Loaders page for the loaders and the contributors.

== Your own invocation

An application that declares its own `GraphQLInvocation` with `@Replaces(DefaultGraphQLInvocation.class)` or `@Primary` wins: the library creates no invocation, logs one INFO line at startup, and the operations run as your invocation decides. A resolver that needs what only the library's invocation provides (a DataLoader, the request, the response or the principal as a parameter) fails the startup with `[execution-context-unavailable]`, and the message names the application's invocation.

== Async resolvers

A resolver that returns a `CompletionStage` (or a `CompletableFuture`), or a reactive type that the library adapts to one (`Mono`, a `Flux` on a list field, and the single-value types of the return type page), is an async field. The library decides this once for each field at startup, from the declared return type, and wraps only those fields. A field with a plain return type, a bean property or an introspected model field keeps the fetcher it had: there is no wrapper and no extra work for it.

The future of an async field can complete on any thread, and graphql-java resolves the children of the field on that thread, without the request's propagated context. The library therefore hands graphql-java a future of its own, which it completes:

* inside the propagated context that the operation captured when it arrived, so that a context element (a tracing span, a logging context entry, the principal) is visible in the children of the field;
* on the executor that runs the operation, when the source completed on a Netty event loop thread, so that a child that blocks does not stall the server. An event loop thread is recognised by the `reactor.core.scheduler.NonBlocking` marker, which Micronaut's event loop threads carry while `micronaut.netty.default-thread-factory-reactor-non-blocking` is `true` (the default). If you turn that setting off, the library can no longer tell an event loop thread from another one and keeps restoring the context but no longer moves off the thread.

snippet::example.tck.AsyncContextScenario[project-base="test-suite", source="test", tags="async-returns", indent="0"]

A future that completes on a thread of your own pool is not moved: its children continue on that pool, with the context restored. Size such a pool for the field and its children. With `executor: none` there is no executor to move to, so only the context is restored.

A few rules:

* An exception that fails the future reaches the error handling as the exception that you threw: `CompletionException` and `ExecutionException` are unwrapped first.
* A future that is already done, without a failure, when the method returns is used as it is, with no cost.
* The cost of an async field that completes on another thread is one small object (the future that the library returns) and its callback, and nothing for a future that is already done. A field that returns `Object` and a `CompletionStage` at runtime is a synchronous field for the library: graphql-java still waits for it, but its children get neither the context nor the move off the event loop. Declare the stage in the return type.
* When graphql-java cancels the future of the field (a timeout, for example), the library cancels the source future, and the adapter of a publisher cancels its subscription.

[[executeOn]]
== @ExecuteOn per field

Most resolvers run on the executor of the operation. A few need another one, for example a bounded pool for a slow backend, or a dedicated pool for blocking JDBC. Micronaut's own `@ExecuteOn("<executor>")` says so; the library has no annotation of its own. Put it on:

* a resolver method, or a resolver class (the method inherits it, and a method's own value wins);
* a `@GraphQLField` method of a model class, or on the model class (it applies to the methods that bind a field).

The library reads the annotation from the bean metadata once at startup and looks the executor up by name through Micronaut's `ExecutorSelector`, which is a bean lookup: there is no reflection and no annotation read per request, also in a native image. What it does:

* A field hops only when its executor is not the executor of the operation. `@ExecuteOn("blocking")` on a field of an operation that already runs on `blocking` costs nothing, and the same holds for any executor that `micronaut.graphql.tools.execution.executor` names. With `executor: none`, or when your own `GraphQLInvocation` runs the operation, every annotated field hops.
* A field without `@ExecuteOn` keeps the fetcher it had: no wrapper, no extra task, no allocation.
* On an async method the method body runs on the named executor: `@ExecuteOn("pool") CompletionStage<Book> book()` calls `book()` on `pool` and then follows the returned stage.
* A field that hops completes its future on that executor, and its synchronous children continue there. Size the executor for the field and for its children; a child that is not annotated does not hop back. The propagated context of the operation is installed in the hop.
* When the executor rejects the task, the field fails with the `RejectedExecutionException`.
* A bean property never hops. `@ExecuteOn` on an accessor that binds a field as a property fails the startup with `[execute-on-property]`: make the accessor a `@GraphQLField` method, or move the field to a type resolver and put the annotation there. `@ExecuteOn` on a model class does not fail for its properties: it applies to the methods only.
* A name that matches no executor bean, and `scheduled`, fail the startup with `[unknown-executor]`, which lists the executor beans that exist. It is the same code as for the `executor` key.
* `@Blocking` and `@NonBlocking` have no effect: the library does not read them. Use `@ExecuteOn`.

The cost of a hop is one task and one future for the annotated field only. The `InvocationBenchmark` of the `benchmarks` module reports the hop; see CONTRIBUTING.md.

== Cancellation

An execution can be cancelled: a WebSocket `complete` and the close of the connection do it (see <<subscriptions,Subscriptions>>). The library then stops starting new work for it: a hop task that has not started is skipped and the operation ends with an error whose `extensions.code` is `EXECUTION_CANCELLED`, the continuation of an async field that completes afterwards is aborted, and the stream of a subscription is cancelled. Synchronous code that is running is never interrupted.

[[fieldDecorators]]
== Decorate the fetchers of selected fields

Cross-cutting logic, such as sanitising arguments, needs to wrap the fetcher of some fields. Do not write it as a `SchemaDirective.everyElement` wiring that wraps every field: such a wiring turns the library's trivial fetchers into non-trivial ones, which loses graphql-java's shortcuts, and adds a call to every field of every request. If you must use `everyElement`, return the element unchanged unless it carries your directive, and prefer a `named` wiring.

A `FieldFetcherDecorator` bean is the SPI for this. The library asks each decorator once for each field at startup, never per request. The decorator returns the fetcher it received, the same instance, for a field it does not select, and a wrapper for a field it does:

snippet::example.tck.FieldDecoratorScenario[project-base="test-suite", source="test", tags="decorator", indent="0"]

* The `FieldDescriptor` that the decorator receives carries the coordinates of the field, its `FieldExecutionKind` (`TRIVIAL` for a property, `SYNCHRONOUS`, `ASYNC` or `STREAM`), whether the schema declares arguments on it, the field executor (the executor that `@ExecuteOn` names when it differs from the executor of the operation, else `null`) and the annotation metadata of the method or property that serves the field.
* A field without arguments and a trivial property fetcher are not offered to a decorator unless it opts in: override `decoratesFieldsWithoutArguments()` or `decoratesTrivialFields()`. A field that no decorator selects keeps its base fetcher, so a property fetcher stays the library's trivial one and costs nothing.
* Decorators wrap outermost. The composition of a field, outermost first, is: the decorators (lowest `@Order` or `Ordered` first), the async boundary, the executor hop of `@ExecuteOn`, the publisher adapter, the method or property fetcher. A decorator therefore sees the whole field, including the hop, and a wrapper it returns runs on the thread that resolves the parent.
* Directive wirings (`SchemaDirective`) are applied when graphql-java builds the schema, after the decorators, so they wrap the decorated fetcher.
* A decorator is a bean found at compile time, so it works in a native image. A decorator that returns `null` fails the startup.

== Kotlin suspend resolvers

A Kotlin `suspend` function is a resolver method like any other, as a query, a mutation or a type resolver method. This is Kotlin only: Java and Groovy have no `suspend`, so unlike the other examples of this guide, the example below exists in the Kotlin suite only. The continuation is not a parameter of the resolver: the field's arguments are the function's parameters, and its declared type is the type of the field. The library decides this once for each field at startup, and the field is an async field (see above), so its children get the propagated context and leave the event loop.

How the coroutine runs:

* It starts on the thread that resolves the field, which is a thread of the request executor, inside the propagated context of the request. A function that never suspends is done when the call returns, at no cost beyond the call.
* The library gives the coroutine a context with the propagated context of the request, the contexts of the `HttpCoroutineContextFactory` beans (the same ones that Micronaut gives a `suspend` controller method), a job of its own and `Dispatchers.Unconfined`. The unconfined dispatcher moves no work to another thread. It makes the coroutine install the propagated context on whichever thread resumes it, so `PropagatedContext` values are visible after `delay`, and inside `withContext(Dispatchers.IO)`, where the context element also reaches the IO thread.
* The coroutine resumes where its suspension point resumes. When it finishes on an event loop thread, the async boundary completes the field on the request executor, as for any async field.
* An exception that the function throws becomes an error of the field, as the exception that you threw. Cancelling the field's future, which graphql-java does on a timeout, cancels the job, so the coroutine ends with a `CancellationException` at its next suspension point.
* A `suspend` function declares the type of its value. It cannot return a `CompletionStage` or a `Publisher` as well, and it cannot be a field of the subscription type: both fail at compile time and at startup with `[unsupported-return-type]`. Return a `Publisher` without `suspend` for a subscription.
* A function with a wrong number of parameters fails with `[argument-mismatch]`, at compile time and at startup, and the continuation is not counted.

The support needs `org.jetbrains.kotlinx:kotlinx-coroutines-core` on the classpath of the application. The library does not depend on it: its support for `suspend` is a bean that exists only when the Kotlin and coroutines classes are present, so an application without Kotlin (and its native image) never links a Kotlin type. Binding a `suspend` function without kotlinx-coroutines-core fails the startup with `[suspend-without-coroutines]` and the dependency to add. A `suspend` function on a model class (a member of an introspected `@GraphQLType` class) is not supported: put it in a type resolver.

== Breaking change

Resolvers run on the blocking executor by default (BC-35). Before, they ran on the event loop. See the migration page for what to check: a resolver that relied on running on the event loop, or on a thread local that is set there, and the thread pool size.
