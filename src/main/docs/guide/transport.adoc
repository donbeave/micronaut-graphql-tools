The library does not own the transports: `micronaut-graphql` serves GraphQL over HTTP and over WebSocket, and the library plugs its execution model into both. This page lists what to configure, and what the library adds. The example applications in `test-suite-java`, `test-suite-kotlin` and `test-suite-groovy` run both transports under an embedded server in their tests.

== HTTP

[source,yaml]
----
graphql:
  enabled: true
  path: /graphql
  graphiql:
    enabled: false
----

* `graphql.enabled` (default `true`) switches the whole GraphQL transport, and the library's invocation with it.
* `graphql.path` (default `/graphql`) is the endpoint. It takes `POST` with a JSON body of `query`, `operationName` and `variables`, and `GET` with the same three as query parameters, where `variables` is a JSON object.
* `graphql.graphiql.enabled` (default `false`) serves the GraphiQL page, at `graphql.graphiql.path`.

The HTTP status of a GraphQL response is `200` also when the response has `errors`: a parse error, a validation error and an error of a resolver all arrive in the body, with `message`, `locations`, `path` and `extensions` as the specification says (see <<errors,Errors>>).

Every operation runs on the executor of `micronaut.graphql.tools.execution.executor`, never on the event loop unless that is `none` (see <<execution,Execution>>). To reach the request in a resolver, use a `GraphQLContextContributor`, which reads the request once and puts what the resolvers need in the GraphQL context of that execution:

[source,java]
----
@Singleton
public class TenantContributor implements GraphQLContextContributor {

    @Override
    public void contribute(GraphQLContext context, GraphQLExecutionRequest request) {
        request.getHttpRequest().getHeaders().get("X-Tenant", String.class)
                .ifPresent(tenant -> context.put("tenant", tenant));
    }
}
----

State that belongs to one request lives in that context, never in a singleton: a singleton is shared by all concurrent requests. The example applications read the user of a request from the `X-User` header in a contributor for that reason.

== WebSocket

[source,yaml]
----
graphql:
  graphql-ws:
    enabled: true
    path: /graphql-ws
    connection-init-wait-timeout: 15s
----

* `graphql.graphql-ws.enabled` (default `false`) turns the `graphql-transport-ws` endpoint on, `graphql.graphql-ws.path` (default `/graphql-ws`) is its path and `graphql.graphql-ws.connection-init-wait-timeout` (default `15s`) is how long a client may take to send `connection_init`.
* The library's handler serves the endpoint. It keeps the operations of each connection apart, runs the events of a subscription off the event loop and cancels the stream when the client sends `complete` or closes the connection. See <<subscriptions,Subscriptions>>.
* `GraphQLConnectionInterceptor` beans accept or reject a connection at `connection_init`.

The deprecated Apollo sub-protocol has its own keys: `graphql.graphql-apollo-ws.enabled` (default `false`), `.path`, `.keep-alive-enabled` and `.keep-alive-interval`. The library sets the `enabled` default itself, so the keep-alive sender of `micronaut-graphql` is not a bean, and an application with no WebSocket server starts without an error, until the application sets `graphql.graphql-apollo-ws.enabled=true` (see <<subscriptions,Subscriptions>>). With the Apollo support on, `graphql.graphql-apollo-ws.keep-alive-enabled=false` switches the sender off.

A connection that sends no `connection_init` within `connection-init-wait-timeout` is closed with code `4408`. A session owns its operations: an operation that completes by itself leaves the session, its id can be used again on the same connection, and a close or a dropped connection cancels the operations that still run.

== Protection and cancellation

`micronaut.graphql.tools.execution.timeout` and the keys under `micronaut.graphql.tools.protection` limit what an operation may cost (see <<protection,Protection>>). A client that closes the HTTP connection, or a WebSocket client that completes or closes, cancels its execution (see <<execution,Execution>>).

== Tested end to end

Each example suite starts an embedded server and talks to it with a real client:

* `HttpTck` (GET and POST, variables and operation name, a moved `graphql.path`, the context of each request, and 400 concurrent requests with distinct contexts and DataLoader registries that never see each other's data);
* `WebSocketTck` (subscriptions with variables and an operation name, a moved `graphql.graphql-ws.path` and the configured initialisation timeout, the connection interceptor, the cleanup of a session on complete, close, a dropped connection and a finished operation, the thread of the events, and concurrent subscriptions that keep their own context);
* `DisconnectTck` (the cancellation on an HTTP disconnect);
* the scenarios `http`, `websocket` and `protection` of the TCK, whose responses are compared as JSON.
