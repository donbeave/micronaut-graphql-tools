The `micronaut-graphql-tools-upload` module accepts files in a GraphQL request. It implements the GraphQL multipart request specification for Micronaut 4: an `Upload` scalar, and a `multipart/form-data` route on the path of the GraphQL endpoint. It is available since 1.0.0-M4.

== The module

[source,groovy]
----
implementation("io.micronaut.graphql.tools:micronaut-graphql-tools-upload")
----

The version comes from the `micronaut-graphql-tools-bom` import of the quick start.

The module reads JSON with the `JsonMapper` API of Micronaut (Micronaut Serialization or any other mapper you have) and uses no Jackson type. The key `micronaut.graphql.tools.upload.enabled` (default `true`) switches the scalar and the route off.

`Upload` is an input type: a field cannot return it, and a query cannot write it as a literal. Both are errors. Read the file inside the resolver: the module discards the files when the response is complete. A file that is mapped to several paths is one object, and Micronaut's `getBytes()` and `getInputStream()` give the content once, so read it once.

== The request

A request follows the https://github.com/jaydenseric/graphql-multipart-request-spec[GraphQL multipart request specification]: an `operations` part with the query, the operation name and the variables (`null` where a file goes), a `map` part that names, for each file part, the paths it replaces, and the file parts. A path starts with `variables`, followed by object keys and list indexes: `variables.file`, `variables.input.cover`, `variables.input.pages.0`. A nullable `Upload` variable may be left out of the map. The files may come before the two JSON parts.

snippet::example.fileupload.UploadTest[project-base="test-suite", source="test", tags="input-object", indent="0"]

A batch (an `operations` part that is an array) is not supported. A request that does not follow the specification is answered with `400 Bad Request` and a body with one error, whose `extensions.code` is `INVALID_MULTIPART_REQUEST` (`GraphQLUpload.INVALID_REQUEST_CODE`): there is no `operations` or `map` part, a part is not valid JSON, the `operations` part has no `query`, the map names a part that the request does not have, a path does not exist in the variables, a path has no `null` placeholder in the variables (the key must be there with the value `null`, as the specification requires), or a part is sent twice.

snippet::example.fileupload.UploadTest[project-base="test-suite", source="test", tags="invalid", indent="0"]

An error of the operation itself (a variable that no file replaces, an unknown field) is a `200` with the usual `errors`, as for a JSON request.

== The route

The transport (`micronaut-graphql`) has a `POST` route on the GraphQL path that consumes every content type and cannot read a multipart body. The module adds a second `POST` route on the same path that consumes `multipart/form-data` only. Micronaut's router picks the more specific `consumes`, so a multipart request reaches the module, and every other request still reaches the transport:

snippet::example.fileupload.UploadTest[project-base="test-suite", source="test", tags="precedence", indent="0"]

The route carries no `@ExecuteOn`. It reads the parts, then calls the `GraphQLInvocation` bean, which hops once to the executor of the library (`micronaut.graphql.tools.execution.executor`, `blocking` by default), so parsing, validation and the resolvers run off the event loop:

snippet::example.fileupload.UploadTest[project-base="test-suite", source="test", tags="executor", indent="0"]

With `executor: none` the operation runs on the thread that completes the request body, as it does for a JSON request.

=== Decoding on the event loop

Micronaut's Netty server decodes the multipart body on the event loop, chunk by chunk as the bytes arrive, and the module does not move that step. It was measured, not assumed: a 160 MB file posted to a local server (Oracle GraalVM 25, Apple M1 Max, the client in the same JVM, so the client competes for the CPU), with a probe request to the same server every 5 ms while the upload ran. With `micronaut.server.multipart.mixed` the probe latency was 4.2 ms at the median and 45 ms at the 99th percentile during the upload, against 3.6 ms and 16 ms when idle; with `micronaut.server.multipart.disk` it was 3.9 ms and 40 ms, against 3.3 ms and 25 ms. The worst probe stayed below 130 ms, so the event loop is never held for the length of the upload: the decoder takes one chunk at a time and returns to the loop between chunks. The cost that remains is the copy of each chunk, and the write to disk when a part goes to disk. If you accept very large files on a server that must keep a tight latency for other requests, put the route behind a limit with `micronaut.server.max-request-size`, and keep the parts on disk so that they are not held in memory.

== CSRF

A `multipart/form-data` request is a simple cross-site request: a page on another origin can submit a form to your endpoint, the browser attaches the user's cookies, and it sends no preflight request first. The multipart route therefore needs an explicit CSRF defence whenever the endpoint authenticates with a cookie or any other credential that the browser sends by itself. CORS does not provide that defence (see <<cors,CORS>>), and the protection that a JSON-only endpoint gets for free does not apply here, because a `Content-Type` of `application/json` forces a preflight. Protect the route with one of these:

* Require a custom request header on it, for example `X-Requested-With` or the header of your CSRF token, in a Micronaut filter that matches the GraphQL path and the `multipart/form-data` content type. A page of another origin cannot add a custom header to a simple request, and adding one makes the request need a preflight. The preflight succeeds only for an origin that the CORS policy allows, so restrict `micronaut.server.cors.*` to trusted origins, or check an unguessable token value rather than only the header's presence.
* Or verify a CSRF token (a synchronizer or double-submit token) on every multipart request, as for any form post.
* Set `SameSite=Lax` or `SameSite=Strict` on the session cookie, and check the `Origin` header against the origins you serve.

An endpoint that authenticates only with an `Authorization` header that the application adds itself (a bearer token) needs none of these, because a cross-site form cannot set that header.

A mutation that takes an `Upload` changes state, so treat the route as you treat any other state-changing `POST`. The transport's `POST` route consumes every content type, so a JSON operation sent with `Content-Type: text/plain` reaches it as a simple request too. A cookie-authenticated mutation needs the same defence on that route, or the server must reject every content type other than `application/json`.

== Cost and limits

The route exists only for `multipart/form-data`: a request of another content type does not touch the module, and the module adds no instrumentation, filter or per-field work. A multipart request pays for reading two small JSON parts and one pass over the map.

The module does not buffer the request itself. Micronaut completes each part as it arrives, under `micronaut.server.multipart.*`: with the defaults a part is kept in memory up to the limit `micronaut.server.multipart.max-file-size`; set `micronaut.server.multipart.mixed` to `true` to keep a part in memory up to `micronaut.server.multipart.threshold` and write the rest to disk, or `micronaut.server.multipart.disk` to `true` to write every part to disk. Use `micronaut.server.max-request-size` to limit the whole request. The parts are held until the operation has run, because the resolver reads them.
