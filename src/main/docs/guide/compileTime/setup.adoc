The compile-time checks read the schema files while the application compiles and fail the build on drift that the startup would also reject: a resolver parameter that names no argument, a primitive at a nullable position, an input class with a property the schema does not define. Each error starts with the code of the check and the schema coordinate, and names the schema file and line. The code and the coordinate are the ones the startup reports for the same fault (see the <<exceptions,error reference>>), so a build error and a startup error are one finding.

The checks are a Micronaut `TypeElementVisitor` in the `micronaut-graphql-tools-processor` artifact. It is the only compile-time engine: the jar registers the visitor and no `javax.annotation.processing.Processor`. A build puts it on the path that its compiler reads Micronaut's processors from, and passes the schema directories as an option (see <<compileTimeOptions,Options>>).

== What a failure looks like

The example suites each keep a resolver that drifts from the schema on purpose. The argument of `Query.searchProfile` is named `limit`, and the parameter is named `count`:

snippet::example.drift.DriftedSearchProfileQuery[project-base="test-suite", source="driftFixture", tags="drifted", indent="0"]

The compilation of this source set fails, and the build prints the code, the coordinate, the Java member and the schema location:

[source]
----
error: [argument-mismatch] Query.searchProfile: the parameter count binds no argument of Query.searchProfile (arguments: contains, limit).
    at example.drift.DriftedSearchProfileQuery#searchProfile(java.lang.String,java.lang.Integer)
    schema src/main/resources/schema.graphqls:11:3
    fix: rename the parameter to an argument name, annotate it with @GraphQLArgument("<name>"), or add the argument to the schema
----

The task `driftFixtureTest` of `test-suite-java`, `test-suite-kotlin` and `test-suite-groovy` asserts this failure, with the `[code] coordinate` line, for each language, and `check` runs it. The fix is the one the message says: rename the parameter, or keep the name and annotate it:

== Set up the build

Add the processor to the path that the compiler of the language reads Micronaut's processors from, and pass `micronaut.graphql.tools.processor.schema.dirs`. Each snippet below is a tagged part of a sample build under `test-suite-build/samples`, and the sample is built by a test, so a documented snippet is one that has run.

TIP: Add the directories of schema that the application adds by code to `schema.dirs` too, so that the checks see it.

=== Switch the checks off

`micronaut.graphql.tools.processor.checks=false` compiles without the checks and prints one note. The startup still runs every check, so the switch only moves a finding from the build to the first start. Each sample passes it from a build property (`-PgraphqlChecks=false` for Gradle, `-Dgraphql.checks=false` for Maven), for example for Gradle with Java:

[source,kotlin]
----
include::{samples}/java-gradle/build.gradle.kts[tags=checks]
----

A build prints one note that names the schema directory of each compilation that runs the checks, so a build log shows whether they ran. A processor that is not on the path of the compiler does not fail anything: it does not run, and no note appears.

== Set up the build for a client

A build that has `@GraphQLClient` interfaces adds the client module and passes `micronaut.graphql.tools.processor.client.dirs`, the directory whose subdirectories are the client schemas (see <<compileTimeClientDirs,Client directories>>). The processor is the one of the sections above, so nothing else changes. Each sample has a client `catalog` with a schema file, an operation file and an interface that selects the schema and the operation by name:

[source,java]
----
include::{samples}/java-gradle/src/main/java/example/CatalogClient.java[tags=client]
----

Edit the document and the compilation runs again: the Gradle snippets below declare the client directory as an input of the compile task, as `schema.dirs` is, so an edited operation or client schema reruns it. Maven does not track the directory, and the Java compiler plugin treats the classes as up to date after an edit, so after an edit of a client document run `mvn clean verify` (the kapt and Groovy builds of the samples see the edit without `clean`, which is the safe command for every Maven build). The Maven snippets read the checks value from a property whose default is `true`; keep that property with the argument. A build prints `checked 1 client operation against 1 client schema.` when the checks ran, and `-PgraphqlClientChecks=false` (Gradle) or `-Dgraphql.client.checks=false` (Maven) switches only the client checks off.
