[[compileTimeOptions]]

The compile-time checks have eight options. Every option name starts with `micronaut.graphql.tools.processor.`, and no other key under that prefix is accepted: an unknown option fails the build with `[processor-option-unknown]`, so that a typo cannot switch a check off. A value that does not parse fails with `[processor-option-invalid]`. A boolean is read as Micronaut reads booleans (`true`, `yes`, `on` and their opposites).

[cols="3,1,1,6", options="header"]
|===
|Option |Value |Default |Meaning
|`micronaut.graphql.tools.processor.schema.dirs` |directories, joined with the platform path separator |none |The directories that hold the `*.graphqls` files, read recursively with the rules of the startup discovery (a `*.graphql` file is not a schema file). The compilation needs it when it has resolver classes: without it the build fails with `[processor-schema-not-configured]`, and a directory that has no schema file fails with `[processor-schema-not-found]`. The directories are an input of the compilation: list every directory that holds schema, also schema that the application adds by code.
|`micronaut.graphql.tools.processor.checks` |`true` or `false` |`true` |`false` compiles without the checks and prints one note. The startup still checks everything. It is the escape hatch of the whole compilation. It is not the runtime key `checks`; see <<keyNames,Key names>>.
|`micronaut.graphql.tools.processor.module.dir` |a directory |none |The project directory of the module that sets `schema.dirs`. A module of a build with several modules sets it, so that a `schema.dirs` that an earlier module compiled in the same JVM left behind fails the build instead of being read. See <<compileTimeSeveralModules,the multi-module rules>>.
|`micronaut.graphql.tools.processor.resolver.accessor.prefixes` |`true` or `false` |`false` |The value of `micronaut.graphql.tools.resolver-accessor-prefixes` that the checks apply when they decide which method binds a field. Set it to the value of the application, or the checks and the startup read different names.
|`micronaut.graphql.tools.processor.loose.nullability` |`fail`, `warn` or `ignore` |`ignore` |What the checks do with a Kotlin type that is stricter than the schema type (`kotlin-nullability-loose`): a non-null return type at a nullable field, or a nullable parameter or property at a non-null position. `warn` reports a compiler warning and `fail` a compile error. The opposite direction, `kotlin-nullability-mismatch`, is always an error. See <<kotlinNullability,Kotlin nullability>>.
|`micronaut.graphql.tools.processor.type.class.convention` |a pattern with `{Type}` once |none |The value of `micronaut.graphql.tools.type-class-convention` that the checks apply when they look for two classes of the module that match one object type of a union or interface (`[ambiguous-type-class]`). Set it to the value of the application. A pattern without `{Type}` fails the build with `[processor-option-invalid]`.
|`micronaut.graphql.tools.processor.client.dirs` |directories, joined with the platform path separator |none |The directories of the client schemas. Each subdirectory is one client schema: its `*.graphqls` files are the schema, and its `*.graphql` files hold the operations and fragments. The reserved name `server` is the schema of `schema.dirs`. A `@GraphQLClient` names its schema with `schema`. The directories are an input of the compilation. See <<compileTimeClientDirs,Client directories>> and the <<clientCompileTime,client checks>>.
|`micronaut.graphql.tools.processor.client.checks` |`true` or `false` |`true` |`false` still parses and assembles every operation of a client, and prints one note, but builds no schema and validates nothing. It is the escape hatch of the client checks; `checks=false` turns them off too. It is not a runtime key.
|===

The names are dot-separated lowercase segments, as every Micronaut `-A` option is (`micronaut.processing.use.context.classloader`, `micronaut.data.jpa.metamodel.enabled`): `javac` accepts only dot-separated identifiers as option names, and Micronaut has no camel case option. The runtime keys of the same settings are kebab-case, so `resolver.accessor.prefixes` is `resolver-accessor-prefixes` at runtime.

[[compileTimeClientDirs]]
== Client directories

`client.dirs` is read by the client visitor, which checks the operations of the interfaces annotated with `@GraphQLClient` (see the <<clientCompileTime,client checks>>). Every entry is a directory, and each subdirectory of it is one client schema, so the same schema name in two entries is one schema read from both:

----
src/main/graphql/client/        <- an entry of client.dirs
  catalog/                      <- the schema named catalog
    schema.graphqls             <- the schema, as many *.graphqls files as it has
    operations/*.graphql        <- operations and fragments, in any subdirectory
  server/                       <- operations of the schema server (it holds no schema)
    health.graphql
----

* `@GraphQLClient(schema = "catalog")` selects the subdirectory `catalog`; the name is the name of a direct subdirectory, not a path. An empty `schema` selects the only subdirectory of the client directories, and fails with `[client-schema-missing]` when there are none or several, naming them.
* The name `server` is reserved: its schema is `schema.dirs`, so an application can check a client of its own schema without a copy of it. A `server` subdirectory of a client directory only holds `*.graphql` files; its `*.graphqls` files are not read. A named operation and a fragment of the schema `server` are read from those directories, so a client directory that is listed and does not exist, or no client directory at all, fails with `[client-schema-missing]` when the operation needs them, also when another listed directory exists. With `client.checks=false` the schema is not built, so `schema.dirs` may be unset: the documents of `server` are read from `client.dirs` alone.
* A client directory that does not exist, a name with no subdirectory and an unset option fail with `[client-schema-missing]` when an operation needs them: a compilation with no client reads no client directory. With `client.checks=false` an inline document needs no directory at all.
* A schema directory without a `*.graphqls` file fails with `[client-schema-missing]`, and a schema that does not parse or build fails with `[client-schema-invalid]`.
* Like `schema.dirs`, `client.dirs` is copied into system properties by Micronaut, so a module of a build with several modules sets `module.dir` as well, and a module that forgot `client.dirs` fails with `[client-schema-missing]` instead of reading the directory of an earlier module.

== Setting `loose.nullability`

The option changes the outcome of a build only for Kotlin, under KSP and under kapt. KSP reads the nullability from the Kotlin declaration; kapt reads it from the `@NotNull` and `@Nullable` annotations of the Java stub of a Kotlin class, so under kapt the check skips the positions that a stub holds no annotation for (a type argument, a type variable, an array and the return type of a `suspend` function), see <<kotlinNullabilityKapt,Under kapt>>. Java and Groovy have no Kotlin nullability, so the option changes nothing there. Its default is `ignore`: the checks report no `kotlin-nullability-loose` finding unless the build sets `warn` or `fail`.

== The module marker

`module.dir` is an option of this library and not Micronaut's `micronaut.processing.project.dir`, because the Micronaut Gradle plugin passes only the incremental, group, module and annotations options and never the project directory. When `module.dir` is absent, the visitor falls back to the project directory that the compiler reports (`VisitorContext.getProjectDir()`), and the marker has no effect when there is none. `module.dir` exists because Micronaut copies the options of a compilation into system properties, and a later compilation of the same JVM (the Gradle daemon and its compile workers, the Maven reactor) reads them when it sets none. A module that forgot `schema.dirs` would then be checked against the schema of the module compiled before it. With `module.dir` set in every module, the visitor compares it with the output directory of the compilation: a value whose directory does not contain the output belongs to another module, and the build fails with `[processor-schema-not-configured]`, naming that directory and the output of this compilation. The rule has limits, and each one keeps or fails safe:

* A module that sets `schema.dirs` without `module.dir` is compared with the project directory that the compiler reports, and is trusted when the compiler reports none and no earlier module of the JVM set `module.dir`. Once one module sets it, a later module that sets only `schema.dirs` fails with `[processor-schema-not-configured]`: set both options in every module.
* A compiler that gives no output directory (kapt and KSP) cannot be compared, so the marker has no effect there.
* `checks=false` is honoured also when an earlier module left it behind: a module that forgot every option is compiled without checks, and the startup still checks every class.
* A module whose output lies inside the project directory of an earlier module is not told apart from it. A build that moves the output of a module outside its project directory sets `module.dir` to a directory that contains it.

The tests that prove it are `MultiModuleGradleSampleTest` and `MultiModuleMavenSampleTest` in the {repo}/test-suite-build/src/test/java/io/micronaut/graphql/tools/buildtools[build-tools tests]: the module that forgot the snippet is built after one that set it, in the same JVM, and its build fails.

== The retired options

`micronaut.graphql.tools.sdlDir` of the earlier annotation processor is retired. A build that still passes it, with the checks on, fails with `[processor-option-removed]` (with `checks=false` nothing reads it), and the message names `micronaut.graphql.tools.processor.schema.dirs`, which replaces it (a list of directories, not one). The rename is entry BC-32 of the migration page. The corpus case that shows it is {repo}/graphql-tools-processor/src/test/resources/corpus/options/removed-option-sdl-dir[`options/removed-option-sdl-dir`].

The three camel case names, `micronaut.graphql.tools.processor.resolverAccessorPrefixes`, `looseNullability` and `typeClassConvention`, are retired the same way: each fails the build with `[processor-option-removed]` and a message `<old name> was renamed to <new name>`, naming `resolver.accessor.prefixes`, `loose.nullability` or `type.class.convention`. The rename is entry BC-46 of the migration page. The visitor still advertises every retired name to the compiler, so `-Werror` does not fail on an unclaimed option when `checks=false` leaves the old name in the build.

A runtime key (`micronaut.graphql.tools.schema.locations`, `micronaut.graphql.tools.strict` and the others) is never a processor option: the checks do not read it, and having one in the system properties of the JVM is not an error ({repo}/graphql-tools-processor/src/test/resources/corpus/options/runtime-key-is-not-an-option[`options/runtime-key-is-not-an-option`]).
