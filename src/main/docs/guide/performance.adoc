This page reports what the repository benchmarks measured for the 1.0 candidate against a baseline, with the settings and the commands to reproduce it. A figure is a measurement of one machine, not a promise: compare runs made on the same machine.

== Where it was measured

[cols="1,3"]
|===
|Candidate |Version `1.0.0-M4` development line, commit `0bc179d5`.
|Baseline |Commit `f1c12a4d`, the first commit that has the JMH benchmarks module (`benchmarks/`). A benchmark that did not exist then has no baseline column.
|JDK |Oracle GraalVM 25.0.5 (HotSpot VM, `25.0.5.0.3+1-LTS-jvmci-b01`), used by both sides.
|Machine |Apple M1 Max, 10 cores, 64 GB, macOS. It was not dedicated to the runs, so read a difference inside the error as noise.
|JMH |1.37, `gc` profiler, 2 forks, 5 warm-up and 5 measurement iterations of 1 s. The figure is the score with the 99.9 percent error that JMH prints.
|graphql-java |Baseline 21.3 (what the transport managed then). Candidate: `default` leg 22.4 (what the transport manages now), `floor` leg 21.5 and `ceiling` leg 26.2.
|===

The baseline and the `default` leg do not run the same graphql-java, so the `floor` column (21.5, the nearest to the baseline) is the check on whether a change comes from graphql-java.

Benchmarks that exist only on the candidate (no baseline), `default` leg, ns per operation and bytes per operation: `injectedParameters` 104.2 ± 12.6 (32 B), `injectedStateParameters` 115.4 ± 11.0 (32 B), `instantCoercion` 178.6 ± 17.6 (144 B), `jsonCoercion` 166.1 ± 14.8 (0 B), `listOfScalarsArgument` 97.8 ± 10.0 (80 B), `localDateCoercion` 70.4 ± 7.6 (112 B), `nestedInputArgument` 445.6 ± 31.2 (120 B) and `recordInputArgument` 390.6 ± 59.1 (96 B). The other benchmarks of the suite (invocation, async boundary, observability, field decorators, security, document cache, binding rules) were not run for this report.

What the figures show, and what limits them:

* The argument conversion and type-resolver method rows are faster by 52 to 72 percent, and the bytes per operation fall with them (for example 264 B to 48 B for an input object). The same rows are as fast on the `floor` leg (graphql-java 21.5), so the newer graphql-java does not explain the gain. The change that produced it was not isolated by a separate measurement here.
* `propertyFetch` and `rootMethod` have no allocation on either side; their time is the cost of the call itself plus graphql-java's own work.
* `graphqlJavaPropertyFetch` runs plain graphql-java with no library code. It moved from 62.2 to 43.2 ns between the two builds with 12 B per operation on both sides. It runs no library code, so the difference is the machine and graphql-java between 21.3 and 22.4; the `floor` leg gives 41.4.
* `unionResolution` and `interfaceResolution` were slower than the baseline on every leg (122.8 and 96.2 ns on the `default` leg) before the resolver cached the resolved object type per schema; with that change (the table) they are below the baseline, with no allocation on either side. These two rows were measured again on the final code; the other rows were measured before it. #744 tracks the remaining check of the replaced-schema case.
* The queries over 1,000 and 10,000 objects are slower on the `floor` leg (3897.0 and 37032.8 µs) than on the `default` and `ceiling` legs. The library code is the same on every leg, so the difference comes from the graphql-java version.

== Allocation gates

`./gradlew :test-suite-benchmarks:allocationTest` passed on the `default`, `floor` and `ceiling` legs, on the same JDK. It fails when an operation allocates more than its baseline in `test-suite-benchmarks/allocation-baselines.properties`.

== Start-up and retained heap

`startup-report.py` (below) binds generated schemas in a fresh JVM per sample, 5 forks per case, `default` leg. The retained heap is the figure to read: it does not depend on the load of the machine. The binding time of this run varies widely between forks (see the minimum and maximum in the script's output; for example the 3,000-field ring schema ranged from 4.1 s to 13.9 s), so no binding time is claimed here. There is no baseline for these benchmarks: the start-up benchmarks do not exist at the baseline commit.

== Reproduce

----
./gradlew :test-suite-benchmarks:allocationTest -PgraphqlJavaLeg=<floor|default|ceiling>
./gradlew :test-suite-benchmarks:jmh -PgraphqlJavaLeg=<floor|default|ceiling> -Pjmh.includes='(Fetcher|Query|AbstractType)Benchmark'
python3 test-suite-benchmarks/scripts/startup-report.py --forks 5
./gradlew :test-suite-benchmarks:jmhJar
java -jar test-suite-benchmarks/build/libs/test-suite-benchmarks-*-jmh.jar '(ContextStart|FirstRequest|StartAndFirstRequest)Benchmark' -f 10 -wi 0 -i 1 -bm ss
----

The baseline numbers come from a checkout of `f1c12a4d` with `./gradlew :benchmarks:jmh -Pjmh.includes='(Fetcher|Query|AbstractType)Benchmark'` on the same JDK. Compare two JMH JSON files with `python3 test-suite-benchmarks/scripts/jmh-compare.py <current.json> --previous <previous.json>`; the `Performance nightly` workflow does the same every night (see `CONTRIBUTING.md`).

== Reads through an interface

A property read through the introspection of an interface is an `invokeinterface` call. On JDK 21 and earlier, a class that is
checked against two interfaces alternately contends on the secondary-super cache of the class; JDK 23 and later do not have
that cost. `InterfaceReadBenchmark` in `test-suite-benchmarks` reads two properties of one interface and then one property of each of two interfaces of the same
class, so the two can be compared on the JDK you run.

Measured with JMH (two forks of five iterations, two reads per operation), reading two properties of one interface and one
property of each of two interfaces of the same class compare as follows:

[cols="1,1,1"]
|===
| JDK | Two properties of one interface | One property of each of two interfaces

| Oracle GraalVM 25 | 5.60 ns | 5.59 ns
| Temurin 21 | 3.61 ns | 4.85 ns
|===
