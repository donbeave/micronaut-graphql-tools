This page reports what the repository benchmarks measured for the 1.0 candidate against a baseline, with the settings and the commands to reproduce it. All figures were measured on one machine. Compare only runs made on the same machine, and read a difference inside the ranges below as noise.

== Where it was measured

[cols="1,3"]
|===
|Candidate |Version `1.0.0-M4` development line, with the merged type resolver cache.
|Baseline |Commit `f1c12a4d`, the first commit that has the JMH benchmarks module (`benchmarks/`). A benchmark that did not exist then has no baseline.
|JDK |Oracle GraalVM 25.0.5 (HotSpot VM, `25.0.5.0.3+1-LTS-jvmci-b01`), used by both sides.
|Machine |Apple M1 Max, 10 cores, 64 GB, macOS. The machine was shared with other work: the one-minute load average read between 6 and 22 around the runs, so many rows were too noisy to use.
|JMH |1.37, `gc` profiler, 2 forks, 5 warm-up and 5 measurement iterations of 1 s. `AbstractTypeBenchmark` runs on 4 threads, the others on 1.
|graphql-java |Baseline 21.3 (what the transport managed then). Candidate: the `default` leg, 22.4.
|===

== Reproduce

----
./gradlew :test-suite-benchmarks:allocationTest -PgraphqlJavaLeg=<floor|default|ceiling>
./gradlew :test-suite-benchmarks:jmh --rerun -Pjmh.includes='(Fetcher|Query|AbstractType)Benchmark'
python3 test-suite-benchmarks/scripts/startup-report.py --forks 5
----

The baseline figures come from a checkout of `f1c12a4d` with `./gradlew :benchmarks:jmh --rerun -Pjmh.includes='(Fetcher|Query|AbstractType)Benchmark'` on the same JDK. Gradle treats an unchanged `jmh` task as up to date and would copy old results, hence `--rerun`. Compare two JMH JSON files with `python3 test-suite-benchmarks/scripts/jmh-compare.py <current.json> --previous <previous.json>`; the `Performance nightly` workflow does the same every night (see `CONTRIBUTING.md`).

== Reads through an interface

A property read through the introspection of an interface is an `invokeinterface` call. On JDK 21 and earlier, a class that is
checked against two interfaces alternately contends on the secondary-super cache of the class; JDK 23 and later do not have
that cost. `InterfaceReadBenchmark` in `test-suite-benchmarks` reads two properties of one interface and then one property of each of two interfaces of the same
class, so the two can be compared on the JDK you run.

Measured with JMH (two forks of five iterations, two reads per operation), reading two properties of one interface and one
property of each of two interfaces of the same class compare as follows:

[cols="1,1,1"]
|===
| JDK | Two properties of one interface | One property of each of two interfaces

| Oracle GraalVM 25 | 5.60 ns | 5.59 ns
| Temurin 21 | 3.61 ns | 4.85 ns
|===

== Union and interface resolution

The type resolver of a union or interface looks the object type up in the schema of the request, so that a schema another
component replaced after the binding is the one that answers. `AbstractTypeBenchmark` measures it on four threads next to two
controls: a resolver that caches the object type per class in a `ClassValue` and never looks at the schema
(`unionResolutionCachedType`), and a resolver that returns one object type (`unionResolutionControl`, the cost of the
benchmark loop itself, about 7 to 8 ns).

The schema check is not where the time goes: the variant without it is as slow as the resolver was, so the cost is the
`ClassValue` lookup. The resolver now also remembers the first two classes that resolve, weakly, so that a hit on one of
them is a reference comparison; any other class takes the `ClassValue`, and a class of a discarded class loader is still
not retained.

Measured with JMH (4 threads, two forks, `gc` profiler, Oracle GraalVM 25.0.5), the resolver before and after run back to
back on one machine under a load average of 6 to 11. The error of one run reaches 8 ns on a shared machine, so the figures
show the direction and the order of magnitude, not a precise difference:

[cols="1,1,1,1"]
|===
| Leg | Resolver | `unionResolution` | `interfaceResolution`

| default | before | 27.5 ns | 26.3 ns
| default | now | 17.5 ns | 17.0 ns
| floor | before | 25.3 ns | 27.6 ns
| floor | now | 23.2 ns | 21.7 ns
|===

The resolver that caches the object type with no schema check measured 25 to 31 ns in the same runs, and the loop control
about 7 to 8 ns.

Allocation is 0 B/op on both benchmarks on both legs.
