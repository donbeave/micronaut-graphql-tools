The compile-time checks read the schema files while the application compiles and fail the build on drift that the startup would also reject: a resolver parameter that names no argument, a primitive at a nullable position, an input class with a property the schema does not define. Each error starts with the code of the check and the schema coordinate, and names the schema file and line. The code and the coordinate are the ones the startup reports for the same fault (see the <<exceptions,error reference>>), so a build error and a startup error are one finding.

The checks are a Micronaut `TypeElementVisitor` in the `micronaut-graphql-tools-processor` artifact. It is the only compile-time engine: the jar registers the visitor and no `javax.annotation.processing.Processor`. A build puts it on the path that its compiler reads Micronaut's processors from, and passes the schema directories as an option (see <<compileTimeOptions,Options>>).

Every statement on this page that says what the checks do, in which language and build tool, or how they behave in an incremental build, links the test or the sample build that proves it. The links point to the build-tools tests of `test-suite-build` (a sample build for each tool, built with Gradle TestKit or Maven), to the binding corpus of `graphql-tools-processor` (the same case compiled and started in each language), or to the three example suites.

== What is checked at compile time

The visitor checks one resolver class at a time, with the per-class rules that the startup uses. The <<exceptions,error reference>> lists every code, and its `Compile time` column says whether the compile-time check reports it. Two groups exist.

*The strict checks that run at compile time.* Five of the ten checks of strict mode are decided by one class and run in the build: `unbound-resolver-method`, `root-method-several-operations`, `unbound-enum-constant`, `unmapped-input-property` and `nullable-primitive`. The other five (`unreachable-type`, `unreachable-value-type`, `unused-dictionary-entry`, `interface-read-through-implementation` and `unwired-directive`) need the whole program and run at startup only.

*The per-class failures.* A method that binds no field, a parameter that binds no argument or binds it twice, the number of parameters, the Java type of an argument or of an input property, the input classes and enums that the arguments reach, the shape of the return type, `@GraphQLSchemaCoordinate`, and the introspection of the classes behind input and enum types are all decided by the class and its types, so they are reported at compile time.

Every compile-time check is the same in the three languages. The corpus compiles each case in each language the case has a directory for and compares the findings with one expected file; a language that differs needs an entry in {corpus}/corpus-language-differences.txt[`corpus-language-differences.txt`], and the list is empty and may only shrink ({repo}/graphql-tools-processor/src/test/groovy/io/micronaut/graphql/tools/corpus/BindingCorpusSpec.groovy[`BindingCorpusSpec`]).

=== The soundness rule

A compile-time error is a finding that the startup also reports at its default severity, with the same code and the same coordinate. The compile-time check never reads the severity settings (`strict`, `checks.<code>` and `allow.*` of the runtime): the five checks above are errors at compile time even where a runtime setting would relax them. A build that is rejected by a check a runtime setting relaxes is rejected on purpose, and the way out is an annotation (see below).

The corpus asserts the rule for every case and language (`BindingCorpusSpec`, rule 5 of the {repo}/graphql-tools-processor/src/test/resources/corpus/README.md[corpus README]). Five documented exceptions remain, each one a case where the build also fails at startup, but with another code first. They are in {corpus}/corpus-soundness-exceptions.txt[`corpus-soundness-exceptions.txt`] with a reason each, and the list may only shrink:

* two resolver classes bind one root field (the startup reports the ambiguity first);
* a `RuntimeWiringCustomizer` claims the field (the startup binds no method to it);
* binding the field throws before the argument rule runs;
* a binding failure of another resolver class stops the startup before the strict checks of this class;
* two resolver classes bind one input type or enum to different Java classes.

=== Only the startup can prove it

`class-not-introspected` is the one finding that a check of one class cannot prove: another class can make a class introspected with `@Introspected(classes = ...)` or `@Introspected(packages = ...)`, and so can a dependency. A `@GraphQLModels` of the same compilation is the exception: the check reads it (wherever in the compilation it is declared) and does not warn about a class it lists. The check also covers the class that a resolver method returns for an object type, with the coordinate of the field; see <<models,Model Classes>>. So the compile-time check reports it as a *warning*, and the startup decides. The walk stops at that finding, as the startup stops at its failure, so the findings of the same class that come after it are the startup's.

A build that turns compiler warnings into errors (`-Werror` for javac) fails on this warning like on any other, because the visitor reports it through the compiler's own warning channel; no sample build runs with `-Werror`, so no test covers that. There, put `@Introspected` on the class itself: a class that carries `@Introspected`, or an annotation that carries it (`@GraphQLInput`, `@GraphQLType`, `@Serdeable`), is seen as introspected at compile time. The corpus shows the finding as a `warning` line in `compile.txt` ({corpus}/README.md[corpus README]).

=== Several modules

A build that keeps resolver classes in feature modules applies the processor in each module that holds resolver classes, and only there: a module without resolvers has nothing to check, and a schema edit does not recompile it. A compilation sees its own sources and its classpath, so the checks split in two.

*What one class determines runs in every module*, whichever module defines the classes it reaches: a method that binds no field, a wrong argument name or type, a primitive at a nullable position, an input class property or an enum constant that the schema does not define, the shape of the return type. The input classes and enums of a dependency are read from its class files. A module that fails fails its own build, with the code, the coordinate and the schema location, and a module that does not depend on it still compiles.

*What needs the whole program never fails at compile time*: a field that no resolver binds (the resolver may be in another module), two modules that resolve one field, a type that nothing reaches, the dictionary and the directives. The visitor never reports a field as unbound because no resolver is in the module. The startup of the application, which sees every module, reports these with the coordinate (`field-not-bound`, `multiple-methods-found`, and the others whose `Compile time` column says `no`).

The schema is a directory of each module that applies the processor: the module sets `schema.dirs` to the directory that holds the schema, for example the source directory of the schema module. A schema that exists only inside a jar of the classpath (`classpath*:` at startup) cannot be read by a compiler plug-in, so a module with resolvers and no directory fails with `[processor-schema-not-configured]`; the explicit way out is `checks=false` there, and the startup still checks everything. === Conditional beans, `@Requires` and `@Replaces`

The visitor checks the class as written. It does not evaluate `@Requires` or `@Replaces`, and it does not know which beans an environment creates: that is a property of the running application. So the facts that depend on the set of beans are the startup's. When a subclass carries `@Replaces(<original>.class)`, the original is dropped at startup and only the subclass binds; when both stay active and bind one field, the startup fails with `[multiple-methods-found]`. Neither outcome is a compile-time finding, because the `Compile time` column of both `multiple-methods-found` and `field-not-bound` is `no`. A conditional bean gets the same per-class compile-time checks as any other bean. A class that `@Requires` excludes in some environment is still compiled with the checks on, so a per-class error in it (an argument that does not match the schema, for example) fails the build although no environment may ever create the bean. This is the documented behaviour, not a gap in the soundness rule: the startup reports the same finding with the same code and coordinate when it binds the class, and a build can only reject what the class itself decides. The corpus cases {corpus}/conditional/per-class-finding[`conditional/per-class-finding`] and {corpus}/conditional/replaces-per-class-finding[`conditional/replaces-per-class-finding`] show a per-class error in a conditional class failing the build, and {corpus}/modules/conditional-replaces-library-resolver[`modules/conditional-replaces-library-resolver`] shows a `@Replaces` of a resolver from another module deciding nothing at compile time. The checks that need the set of beans (`multiple-methods-found` and the other whole-program findings) run at startup only, where the conditions decide which beans count. If a module holds classes that must compile without checks, keep them in a module that does not apply the processor, or set `checks=false` there.

=== Customizers

A customizer (a `SchemaMappingDictionaryCustomizer`, a `RuntimeWiringCustomizer`, a customizer of the registry) adds schema or wiring that no schema file holds, and the compile-time checks do not see it. The checks read the files of `schema.dirs` only, and there is no option that makes the visitor run a customizer. A field that a customizer claims is the case of the `RuntimeWiringCustomizer` soundness exception above. Keep the schema a customizer adds in files and list their directory in `schema.dirs`, or leave that part to the startup.

=== The escape hatches at compile time

The way out of a compile-time check is an annotation on the code, not a setting: the compile-time check does not read `strict`, `checks.<code>` or `allow.*`. `@GraphQLArgument("<name>")` binds a parameter whose name is not the argument's, `@GraphQLSchemaCoordinate` binds a method to a field explicitly, `@GraphQLIgnore` takes a public method out of binding, and `@Introspected` on the class makes it introspected (see above). `checks=false` is the one switch for a whole compilation.

=== Parameter names

A method declared in the sources that Micronaut processes (Java, Kotlin or Groovy) binds by the name in its source: no `-parameters` flag is needed. The corpus compiles Java without `-parameters` and Groovy without `parameters`, so its `argument/` cases show it. The flag is needed for one case only: a method inherited from a class file without parameter names, such as an interface method of a dependency. See <<inputs,Inputs>>, "Where the names come from".

== Incrementality

The visitor is isolating: it checks each resolver class on its own, so an incremental compilation checks the classes that changed. {tests}/IncrementalCompilationContract.java[`IncrementalCompilationContract`] proves what that means for each Gradle sample (Java, kapt, KSP and Groovy). It builds a copy of the sample with 22 classes twice, once with the processor and once as a control without it, and applies the same edits to both. The set of class files that an incremental build rewrote (modification time, size or presence) must be the same in both, so the visitor makes the compiler redo no work that it would not redo anyway.

[cols="3,5", options="header"]
|===
|Edit |What the test asserts
|The body of a bean, the body of the resolver |The rewritten class files equal those of the control build.
|The binary interface of `Book` |The same.
|A new class with a stereotype that the visitor does not claim |The same.
|A deleted class |The same.
|Every state, built from scratch in a copy |It passes: an incremental build never fails where a clean build of the same sources passes.
|A schema edit that drifts the resolver |The incremental build fails with the code and the coordinate, and the repair passes.
|A schema edit (Gradle) |The checked task reruns, because the build declares the schema directory as an input ({tests}/GradleSampleContract.java[`GradleSampleContract`]); with nothing changed the task is up to date.
|A schema edit (Maven) |A build without `clean` can pass on the old result: see the Maven rule below.
|===

The tests assert no wall-clock time. They record the clean and the incremental time with the JDK and the load of the machine in `build/reports/build-tools/outcomes.txt`, so a number is quoted with its context or not at all. The checks add no build cache problem: a clean rebuild takes the checked javac task from the build cache, and so does the same project at another path, because the schema input is path sensitive by its relative path ({tests}/GradleSampleContract.java[`GradleSampleContract`] asserts `FROM_CACHE` for the Java sample, `aCleanRebuildAndARelocatedProjectUseTheBuildCache`). For the kapt, KSP and Groovy tasks the tests record the outcome and assert only that the task passes: they take the absolute path of the schema as an input.

=== The Maven rule

Maven does not track the schema directory. The compiler plugin of a Java project calls the classes up to date after a schema edit, so run `mvn clean verify` after a schema edit. What each sample does without `clean` is asserted in {tests}/MavenSampleContract.java[`MavenSampleContract`]: the Java sample passes on the stale result, and the kapt and Groovy samples run again and fail on the drift. The documented rule is the same for all three: clean after a schema edit. The startup runs every check in any case.

== Native image

The compile-time checks run in the compiler and add nothing to the application at runtime: the processor goes on the compiler path (`annotationProcessor`, `ksp`, `kapt`, `compileOnly`, or Maven's `provided`), not on the runtime classpath, and the module depends on no runtime class. The visitor writes no file. It writes the type resolver contracts that a bean class inherits into the annotation metadata of the class (`@ResolverContracts`), which the startup reads from the bean definition without reflection, so a bean that is a type resolver only through an inherited annotation binds the same way on the JVM and in a native image. A build that does not run the processor fails such a bean at startup with `[type-resolver-contracts-not-found]`, which names the processor. The rule that the library uses no reflection is enforced by `ArchitectureRulesSpec` (see <<nativeImage,Native Image>>).
