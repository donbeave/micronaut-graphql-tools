The library checks that the code and the schema agree, and it fails early when they do not. Three layers do it, from the earliest to the latest:

. The <<compileTime,compile-time checks>> reject, in the build, the faults that one resolver class decides on its own.
. The startup binds every schema field and runs the strict checks. A fault fails the start of the application, so a broken binding never serves a request.
. The <<manifest,binding manifest>> records what the binding did, so that a review can see a change of binding as a change of a line.

== When a fault fails

*With the compile-time checks*, a fault that one class decides fails the build, with the code and the schema coordinate of the finding. The five strict checks `unbound-resolver-method`, `root-method-several-operations`, `unbound-enum-constant`, `unmapped-input-property` and `nullable-primitive` and the per-class failures belong to it (see <<compileTime,Compile-Time Verification>>). A fault that needs the whole program passes the build and fails at startup.

*Without them*, the same fault fails when the schema is bound. By default (`micronaut.graphql.tools.eager-init: true`) that is when the application context starts, so the application, and the embedded server with it, does not start. The first request does no binding work. With `eager-init: false` the schema is bound when the first bean that needs the `GraphQLSchema` is created. See <<startupErrors,Startup Errors>>.

The compile-time checks never relax a finding that a runtime setting relaxes: they ignore `strict`, `checks.<code>` and `allow.*`. A finding that they report is suppressed by an annotation only.

== Migrating an application that fails the checks

An existing application can fail many checks at once. Relax them, collect the findings, and tighten again:

CAUTION: `strict: false` turns every check into a warning, `unwired-directive` included. An application that relies on a custom directive for authorization would serve its annotated fields without the directive while the recipe runs. Keep `checks.unwired-directive: fail` in that case (an explicit `checks.<code>` entry wins over `strict`), or run the migration on an instance that no client can reach.

. Set `strict: false` and `precedence: resolver-first`. Every check that has no `checks.<code>` entry is then a warning (see the caution above), and a field that a property and a resolver method can both bind goes to the resolver method.
. Set `manifest.enabled: true` and a `manifest.path`, and start the application. Each finding is a line that starts with `!` in the manifest.
. Fix, annotate or allow each `!` line: fix the code or the schema, put `@GraphQLIgnore` on a member that binds no field on purpose, or list the line of a check in `allow.findings`. A `!precedence-ambiguity` line is not a check, so `allow.findings` rejects it with `[invalid-allow-findings]`: resolve it with a `@GraphQLSchemaCoordinate`, a `@GraphQLIgnore` or a resolver directive, or keep `precedence: resolver-first` as the decision.
. Remove `strict: false`, and then `precedence: resolver-first` when no field needs it.
. Add `micronaut-graphql-tools-processor` once the findings of the startup are fixed (see <<compileTimeSetup,Set up the build>>). A class that the checks reject at compile time was in general already a finding of the startup, with documented exceptions that fail the build only (for example a `RuntimeWiringCustomizer` that claims a field, or a Kotlin nullability mismatch, which only the compiler sees; see <<compileTime,The soundness rule>>). Fix them in the code, or compile that module with `micronaut.graphql.tools.processor.checks=false`.


[configuration]
----
micronaut:
  graphql:
    tools:
      strict: false
      precedence: resolver-first
      checks:
        unwired-directive: fail # keep it when a directive guards access
      manifest:
        enabled: true
        path: build/graphql-binding-manifest.txt
----

`strict: false` does not relax a binding failure: every schema field must be bound (`[field-not-bound]`) in every mode.
