A field of the `Subscription` type streams its events to the client over a WebSocket. The library serves the `graphql-transport-ws` protocol itself, in its own handler, and runs every subscription through the same invocation as a query, so the execution model of the <<execution,Execution>> page holds for each event: no resolver runs on the event loop, and the context of the connection is there.

== Enabling the endpoint

The transport of `micronaut-graphql` owns the switch and the path, and the library keeps them:

[source,yaml]
----
graphql:
  graphql-ws:
    enabled: true
    path: /graphql-ws
    connection-init-wait-timeout: 15s
----

* `graphql.graphql-ws.enabled` (default `false`) turns the endpoint on.
* `graphql.graphql-ws.path` (default `/graphql-ws`) is the path of the WebSocket. The sub-protocol is `graphql-transport-ws`.
* `graphql.graphql-ws.connection-init-wait-timeout` (default `15s`) is how long a client may take to send `connection_init` before the server closes the connection with `4408`.

The library replaces the handler of `micronaut-graphql` for this endpoint, with `@Replaces`, whenever the endpoint is enabled. That handler cannot open a connection on Micronaut Core 4.10 (it asks the codec for an abstract message type, so a client that connects is closed with `1011`), and it keeps the running operations in one map for all connections, so a client that reconnects and reuses an operation id is closed with `4409`. The library's handler reads the message as text and keeps its state per connection.

The deprecated Apollo `graphql-ws` sub-protocol (`graphql.graphql-apollo-ws.enabled`) stays with the transport. Its operations reach the library's invocation too, so they run on the executor like every other operation.

== Writing a subscription

A method of a `SubscriptionResolver` (or of a `@GraphQLRootResolver` class) that is named after a field of the `Subscription` type returns a reactive stream of the event. `Publisher<T>`, Reactor's `Flux<T>` and the other reactive types that Micronaut converts to a `Publisher` are accepted.

snippet::example.tck.WebSocketScenario[project-base="test-suite", source="test", tags="ws-subscription", indent="0"]

The method itself runs on the executor of the operation (`micronaut.graphql.tools.execution.executor`). The library wraps the stream it returns once for each subscription:

* the events are moved to that executor, in order, so that the fields of the event are resolved there and a child that blocks does not stall the event loop, even when the source emits on an event loop thread, as above (a Reactor timer emits on a thread that declares itself an event loop thread);
* the `PropagatedContext` that the operation captured is installed where the fields of each event are resolved, so `ServerRequestContext.currentRequest()` returns the upgrade request of the connection, with its headers;
* cancelling the subscription cancels the source. With `executor: none` the events are not moved.

The cost is one wrapper and one queue for each subscription, and one executor task for each burst of events; fields do not hop.

A query or a mutation can be sent over the same connection: it is one execution with one `next` and then `complete`. A resolver that blocks runs on the executor, not on the event loop, as it does over HTTP.

The library adapts the flow to a `Publisher` once for each field at startup, with `asPublisher` of kotlinx-coroutines-reactive, and the adapted stream takes the same path as any other subscription (see above):

* the flow is collected once for each subscription, by one coroutine, and a method that does not return a `Flow` gets no wrapper;
* the coroutine runs in the propagated context of the operation and in the contexts of the `HttpCoroutineContextFactory` beans, as a `suspend` resolver does, so the context is visible inside the flow, also after `flowOn` or `withContext`;
* the events are moved to the executor of the operation and the fields of each event are resolved there, off the event loop, with the context of the connection;
* a `complete` from the client or the close of the connection cancels the subscription, which cancels the coroutine that collects the flow: the `CancellationException` reaches the flow, so its `onCompletion` and `finally` blocks run.

A `Flow` is accepted on a field of the `Subscription` type only. On any other field, inside a list or inside a `CompletionStage`, it fails the startup with `[unsupported-return-type]`: return the value from a `suspend` function, or a `Publisher`, instead.

The adapter needs `org.jetbrains.kotlinx:kotlinx-coroutines-reactive` on the classpath of the application, next to kotlinx-coroutines-core. The library does not depend on it: the adapter is a bean that exists only when those classes are present, so an application without them (and its native image) links no Kotlin type. Binding a `Flow` subscription without it fails the startup with `[flow-without-reactive-coroutines]` and the dependency to add.

== Accepting a connection

A browser cannot set a header on a WebSocket, so clients put the token in the `payload` of the `connection_init` message. A `GraphQLConnectionInterceptor` bean (package `io.micronaut.graphql.tools.websocket`) sees that payload and the HTTP request that upgraded the connection, and answers with `GraphQLConnectionResult`:

* `accept()` or `accept(attributes)` acknowledges the connection. The attributes (the user that the token names, for example) belong to the connection and are given to every operation of it, as the connection attributes of the execution.
* `reject()` closes the connection with `4403` and the reason `Forbidden`; `reject(code, reason)` picks a code between `4000` and `4999` and a reason.

snippet::example.tck.WebSocketScenario[project-base="test-suite", source="test", tags="ws-interceptor", indent="0"]

With several interceptors, they are called in the order of `@Order` (lowest first) until one rejects, and the attributes of the accepting ones are merged. An interceptor runs on the executor, so it may block, for example to validate a token against a service. An exception that it throws rejects the connection with `4403` and a generic reason, and is logged at WARN. Without an interceptor every connection is accepted.

A client must wait for `connection_ack` before it sends `subscribe`: a `subscribe` that arrives earlier closes the connection with `4401`.

== The connection and its operations

Each connection keeps its own state, in the attributes of its `WebSocketSession`: the acknowledgement, the connection attributes and the running operations by id. Two connections never see each other's operations: a `complete` for the id `1` completes the operation `1` of the connection that sends it, and nothing else. When the connection closes, every operation of it is cancelled and the state is released.

[cols="1,3", options="header"]
|===
| Close code | Meaning
| `4400` | The message is not valid JSON, has no known `type`, or lacks the `id` or the `query` that its type needs.
| `4401` | A `subscribe` arrived before the connection was acknowledged.
| `4403` | An interceptor rejected the connection (default code).
| `4408` | No `connection_init` within `connection-init-wait-timeout`.
| `4409` | An operation with that id is already running on the connection.
| `4429` | More than one `connection_init`.
|===

An operation that does not parse or validate is answered with an `error` message and ends. A result of an executed operation, also one with field errors, is a `next` message; the operation ends with `complete` (the client's own `complete` is not answered). If the publisher of a subscription fails, the client receives an `error` message whose payload is the list of errors that the default error handling makes of the exception, the same as for a query (see the Errors page); an exception that no mapper handles is the generic `INTERNAL_ERROR` error without its message, and the library logs the cause.

== Cancellation

A `complete` from the client and the close of the connection cancel the operation: the stream is cancelled upstream (a source that releases resources on cancel does), and the execution is marked cancelled, so that a hop task that has not started is skipped (the operation then ends with the error code `EXECUTION_CANCELLED`) and the continuation of an async field that completes afterwards is aborted. Cancellation is cooperative: synchronous code that is already running is never interrupted.

== Over WebSocket, the response is not there

The upgrade request is available to resolvers, the HTTP response is not: it does not exist for a message of an open connection. The connection attributes are the way to carry what the handshake learned.

== Native image

The handler uses no reflection: it reads and writes the messages as maps through the `JsonMapper` of the application, and the same end-to-end checks run in the native test of the Java and Kotlin example suites.
