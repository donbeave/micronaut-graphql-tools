# micronaut-graphql-tools 1.0.0-M3 release notes

Not released yet. Tag `1.0.0-M3` will be published to the GitHub Packages Maven registry of this repository by the `Release` workflow (D-40). This milestone follows [1.0.0-M2](RELEASE-NOTES-1.0.0-M2.md). The numbering continues from the M2 notes: `BC-01` to `BC-19` are described in the M1 notes, `BC-20` in the M2 notes, and `BC-21` to `BC-29` are the numbered changes of this milestone so far. See the migration page for the fix of each change. This file grows as the milestone's changes land.

## What this release changes

- Precedence (#105, BC-29): one rule for object and interface fields. A field that a member of the Java type and a type resolver method can both bind fails the startup under `precedence: fail` (the new name of the default `strict`), and the type resolver method wins, with no ambiguity, when the field carries a resolver directive or the method declares its coordinate with `@GraphQLSchemaCoordinate`; a member marked `@GraphQLIgnore` binds nothing. `precedence` stays independent of `strict`. Decided at startup; the request path is unchanged.
- Input omission (#159, BC-28): `ArgumentValue` needs no option. The converter of an input type handles omission only when that type has an `ArgumentValue` property or constructor parameter; a type without one runs no omission code, and a `List<String>` argument allocates nothing for it (the allocation baselines are unchanged).
- Performance (D-02): a GraphQL enum is wired with a values provider built at startup from the enum's bean introspection, so an enum argument reaches the resolver as the Java constant without a conversion call. The allocation baseline of the enum argument case drops from 504 B to 24 B (#33).
- Performance (D-02): arguments and input objects are converted by converters that startup builds from the declared type and the bean introspection, so a request runs no Jackson `convertValue` and no reflection. The allocation baselines drop, per operation: a scalar argument 504 B to 24 B, an input object 728 B to 48 B, a list of four input objects 1,648 B to 176 B (#37).
- Safety (#86): per-check severity. `micronaut.graphql.tools.checks.<code>` is `fail` (the default), `warn` or `ignore` for each of the ten checks, `strict` is the shorthand for the checks without an entry, and `allow.unreachable`, `allow.inert-directives`, `allow.schema-customizer-directives` and `allow.findings` (lines of the binding manifest) accept findings. Every entry is validated at startup. A check at `ignore` does no work. Documented in the configuration reference and the migration page.
- Diagnostics: one code registry for the strict checks and the startup failures, `BindingCode` in `graphql-tools-binding` (#237). Every startup message starts with `[code]`, `SchemaBindingException#code()` returns it, the `!` lines of the binding manifest are named by it, and the compile-time diagnostics use the same codes. The error reference lists them.
- Schema discovery (#17): without a `TypeDefinitionRegistry` bean the library reads `micronaut.graphql.tools.schema.locations` (default `classpath:graphql/**/*.graphqls`; `classpath*:` for dependency jars, `file:` for the file system) and merges the files, each parsed with its own name. A schema without a `schema { }` block uses `Query`, `Mutation` and `Subscription` as root types. A file that holds only operations is skipped. A native image reads the schema index `META-INF/micronaut-graphql-tools/schema-index.txt`. The compile-time processor reads its schema directory with the same code.
- Input conversion errors (#175): a value that does not convert (a custom scalar value that is not accepted, a list where a `Map` is declared, an input class that rejects a value) is a GraphQL error of the field with `extensions.code` `INPUT_CONVERSION_FAILED`, the coordinate `Type.field(argument)` and the path inside the value. The message has no Java class name and no stack detail; the cause is logged at debug level. The other fields still resolve. Before, the raw exception message reached the client in graphql-java's generic data fetching error.
- Binding manifest: the format is specified in the guide page "Binding Manifest" and versioned in its first line, `# graphql-binding-manifest 2` (#90, BC-25). The schema hash does not depend on the order of the schema files and extensions, a `scalar` line names the scalar and not the `Coercing` class, the text is ASCII, and the examples of the specification are golden files. A start that does not record the manifest still costs nothing. The graphql-java line of the header stays `unknown` on graphql-java 26, whose jar declares no version.

## Other behaviour changes

- An application with no `TypeDefinitionRegistry` bean now reads the default schema location instead of failing with a missing bean. When no file is found the startup fails with `SchemaDiscoveryException` (code `schema-not-found`).
- A schema without a `schema { }` block binds. Before, `SchemaDefinitionNotProvidedException` failed it; it now fails only a schema that has no `Query` type.

## Known limitations

- The compile-time manifest that the JSR-269 processor writes keeps the old words of the `!` lines until #144 removes the processor.
- The diagnostics of the JSR-269 processor keep their `[graphql]` prefix until #144 removes it; the visitor that replaces it reports `[code]` from the registry.
- `@GraphQLIgnore` and the lifecycle exclusion (#106) are applied by the visitor. The JSR-269 processor, which the build still runs, does not read `@GraphQLIgnore` and reports `@EventListener`, `@Scheduled` and `@PreDestroy` methods of a root resolver as unbound in strict mode until #291 makes the visitor the default.
- The five compile-time checks are not relaxed by `checks.<code>`: the compile-time error stays (D-39); the JSR-269 processor keeps its own options until #291.
